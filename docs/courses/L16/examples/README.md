# L16 恢复实验：校验成功，为什么仍不能替换当前库？

这组实验调用仓库实际备份服务，在全新教学目录创建商品和入库记录。它用于理解恢复点与新增业务事实，不是生产回滚，也不证明双系统冷启动完成。

## 先预测

商品先入库8件，生成一致性备份，再入库2件。现在把备份恢复到另一个目录：恢复库应该有8件还是10件？如果恢复服务报告成功，能否立即把当前库换成恢复库？先写下判断，再运行。

## 运行与观察

在仓库根目录，使用项目虚拟环境运行。每次使用尚不存在的输出目录；程序会拒绝重复目录，以保留上次记录。

**Windows（PowerShell）：**

```powershell
.\.venv\Scripts\python.exe -X utf8 docs/courses/L16/examples/restore_lab.py --output-dir .runtime/l16-restore-trial-01
$LASTEXITCODE
Get-Content .runtime/l16-restore-trial-01/report.json
```

**macOS（zsh）：**

```zsh
./.venv/bin/python -X utf8 docs/courses/L16/examples/restore_lab.py --output-dir .runtime/l16-restore-trial-01
printf '退出码：%s\n' "$?"
cat .runtime/l16-restore-trial-01/report.json
```

程序只使用这个新目录。它依次建立数据、备份、增加业务记录、恢复到独立位置，再检查两种错误操作。没有自动替换运行中的数据库。

| 阶段 | 在库量 | 入库事件 | 应作的判断 |
|---|---|---|---|
| 备份点 | 8 | 第一笔8件 | 这份备份能覆盖的业务事实 |
| 当前源库 | 10 | 第一笔8件、第二笔2件 | 备份之后仍有新业务 |
| 恢复副本 | 8 | 只有第一笔8件 | 恢复回到备份点，不包含后来2件 |
| 再次向同一目标恢复 | 仍为8 | 目标指纹不变 | 默认拒绝覆盖已有库 |
| 损坏副本恢复 | 不产生目标库 | 原备份仍可校验 | 损坏文件被拒绝，失败后也要查状态 |

`restore_integrity.ok` 为真说明数据库结构检查通过。你还要比较商品、数量和事件键；只看到“ok”就替换当前库，会把后来2件的业务事实丢掉。课堂可让同伴把后续入库数量改成另一值，再解释恢复副本为何仍保持备份点数量。

## 实际参考记录怎样使用

讲师本机历史记录 `restore-observation.json` 保留了8、10、8的结果以及两次拒绝后的状态，不随 Git 发布。[记录排版截图](../assets/latest/restore-observation.png)便于课堂阅读，它不是原生工作台页面。学生沿[当前实践手册](../实践操作手册.md#lesson-goals)在本人隔离目录生成恢复与拒绝记录。

先用自己的输出对照参考，再说明差异。一次本机独立恢复不证明容器可构建、整套环境可重建、身份权限已验证，也不证明存在可接受的生产数据损失方案。最终答辩仍需完成本讲规定的冷启动、现场新需求、失败打回、导出与反馈。
