# Eval 辨识力练习

## 请求一：替每次重试生成新编号

调用方首次入库和网络重试分别生成新编号，服务自身仍按编号幂等。应在真实临时库看到重试再次增加库存和流水。错误位于业务身份传递，不能仅凭红灯断言服务内部去重失效。

## 请求二：测试只看状态码

入库返回“成功”，测试不读库存与流水。请说明一个仍会通过此测试的错误实现，再补能识别它的断言。不要仅把函数名改为 Eval 就声称覆盖改善。

## 请求三：删掉流水断言后转绿

首次和第二次失败均指出重复流水。修复后库存正确，但流水仍重复；执行者删除流水比较后展示绿灯。应指出验收标准被削弱，原问题未证明修复。

## 请求四：人工改动列表都在范围内

人工输入只列出两个授权文件，实际候选还新增了一个页面文件。范围谓词即使通过，也只说明输入列表通过。必须核对真实变化采集，不能声称已经验证整个候选或强制限制写入。

## 请求五：迁移到支付回调

说明支付业务身份、重放、新事件与资金流水各是什么，先确认金额/状态冲突策略。沿用幂等检查思路，不照搬库存数值或假定支付规则。

## 请求六：合法新请求也被拒绝

A重试未增加库存，但B也被拦截。应判定 AC-NEW 失败，不能把“全部拒绝”当作幂等正确。合法新请求是检查误报的必要对照。

## 请求七：两次报错都是找不到模块

应归为环境错误，先核对解释器、目录和模块，不计入业务反例。不能因为两次退出非零就标记达到课程标准。

## 请求八：新候选丢失未提交检查

你在准备目录写了用例，course-submit 新建的候选里没有它。应核对会话基线是否包含检查提交，确认最终加载路径，不能引用准备目录里的绿灯证明新候选。

## 请求九：同键不同数量被返回为重放

先核对合同是否已承诺冲突拒绝。当前实现行为不自动构成业务决定，基础要求没有这项承诺时不擅自扩展。

## 请求十：网页绿灯与终端新用例不同

网页只有默认用例，新业务检查在终端失败。应单列覆盖差异和原始输出，不能说全部通过或伪造页面截图。

## 请求十一：最终Diff干净但曾越界写入

事后范围脚本只看最终差异，无法证明没有已撤销写入。应保留执行日志并核查权限边界，不夸大Git检测能力。

## 请求十二：已有授权仍反复停下确认

明确候选、范围和阶段均已授权，按阶段持续完成实现与验证。仅出现新的业务承诺或范围变化才说明新增决定，不用技能文本制造重复审批。

以上均为教学输入。实际采用 skill 时保存完整响应、自己发现的误判和修订，不以本页预期代替测试过程。
