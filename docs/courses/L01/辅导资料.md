# L01｜以终为始：一次可验证的 AI 交付怎样完成？

昨天请 Codex 写了一个小工具，今天继续时却说不清：当时要解决什么问题，改了哪些文件，失败在哪里，最后依据什么接受。翻聊天能找回一些句子，却很难把“要求、改动、检查、决定”对应起来。

本讲就从这个现场开始。你先用 Codex 建一个能保存开发记录的个人工作台，再用刚建成的工作台记录它自己的开发过程。今天只建设工作台的终端记录能力，不接入 FlowERP；到 L04，才第一次通过工作台开发这个客户产品。

<a id="lesson-goal"></a>

## 1｜可验证的交付，究竟要验证什么

一次交付可以沿着四个问题核对：**要求是什么，实际改了什么，怎样检查，谁作了接受决定。**少了要求，测试可能检查错目标；少了改动，无法判断是否越界；少了检查，只剩开发者的自述；少了人的决定，结果只能停在待审核。

例如，我们要“保存任务，关闭程序后仍能查回”。Codex 说“保存成功”只是一个回答。真正需要的观察是：退出原进程，再启动新进程，读取同一个数据目录，比较任务编号、创建时的需求和原始检查记录。检查对象是程序行为，不能用一句回答替代。

全课程有三种不同角色。**Codex**协助调查、设计、编码和运行工具；**工作台**保存任务、组织后续执行与审核；**FlowERP**是处理库存、订单、采购的独立客户产品，用业务结果检验交付。你决定问题、范围和接受理由。L01 中工作台还不存在，所以先由你直接监督 Codex 建设它。

![个人研发工作台参考界面](assets/final-deliverables/workbench-overview.png)

**图 1-1　个人研发工作台参考界面。**这是后续网页形态的参考图（2026-09-05）。先认出项目、任务和验收入口；本讲交付的是终端里的 Workbench V0.1，即初始化、项目登记、任务账、命令证据账和状态查询。L04 的 Workbench V0 另补执行与审核，两个名称表示课程建设阶段。

课程采用 FDE（Forward-Deployed Engineering）的现场、交付、能力三循环。本例中，“隔天找不到依据”是现场问题；“重启仍能查回”是交付结果；把它做成以后都能使用的记录工具，是能力增长。后续 FlowERP 的失败还会推动工作台升级。这种增长来自实践、代码和规则的修订。

## 2｜把一句诉求变成你能作决定的问题

“帮我搭建个人 AI 研发工作台”有很多可能答案：聊天整理器、网页任务板、自动编程平台都可能被这样称呼。先不要选技术，先回答“下一次接手时，我究竟缺什么”。

让 Codex 访谈你的真实痛点：要找回任务标题，还是当时的完整要求？失败记录还要不要保留？关闭程序后是否继续保存？同一个编号能否重新使用？Codex 可以给方案，你需要选择第一版的范围，并说明理由。

例如，你决定先保存需求副本和检查记录，不做全文搜索，也不自动执行代码。这一取舍降低了第一版的实现范围，但保留了接手开发所需的依据。把决定写进 **Spec，也就是本次需求说明** `WORKBENCH_SPEC.md`，让每项关键要求都能回指“原始痛点—Codex 建议—本人选择”。文件开始时并不存在，应由这次访谈形成。

验收项需要具体到能比较。把“保存可靠”改成：“创建任务 A，追加一次失败记录，结束程序；新进程查询 A，需求和失败记录保持原样。”再补：“用 A 创建不同内容应拒绝，查询原 A 不变。”前一句验证保存，后一句保护已保存的历史。A 是教学编号，这些都是设计预期，不是已经发生的学生记录。

<a id="workbench-method"></a>

## 3｜先分清三类记录，再决定代码怎样分工

**项目**是会持续开发的对象，例如个人工作台；**任务**是某一次有边界的工作，例如建设 V0.1；**运行记录**是某次检查的命令、输出、退出码和时间。一个项目有多项任务，一项任务可以多次检查。失败后修订再检查，应增加新记录，才能看到前后变化。

![项目、任务与运行记录的关系](assets/technical/03-object-relations.png)

**图 1-2　项目、任务与运行记录的关系。**任务关联项目，也保存创建时的需求快照；多次运行记录关联同一任务。快照就是当时内容的副本。退出码是程序结束时返回的整数，具体含义要结合该命令判断。

为什么要保存需求内容，而不只保存路径？假如今天任务 A 指向 `WORKBENCH_SPEC.md`，明天你改了这个文件，只存路径就会让昨天的任务读到明天的要求。保存内容副本后，外部文件可以继续演进，旧任务仍有自己的依据。参考实现还保存内容哈希，可用于核对副本是否变化；哈希是根据内容计算的标识，内容改了通常就会变，但它不判断需求是否合理。

在写代码前，先确认最小分工：命令入口接收参数；任务逻辑核对编号和关联；存储负责保存与读回；测试比较约定行为。显示格式改变时，不应另写一套保存规则。用少量函数和模块即可，实际位置与理由记入 Spec 的约束。

<a id="v01-design"></a>

## 4｜持久化不只是“生成了一个文件”

**持久化**指数据离开当前进程后仍能恢复。程序内的变量会随退出消失，本地文件或数据库才承担保存。课程参考实现用 SQLite：数据库保存在本地文件中，无需单独数据库服务。你应按自己的合同核对实现，而不是把参考代码当成已完成的个人成果。

本讲五个操作构成一条连续路径：初始化工作台，登记项目，在该项目下创建任务，为任务追加运行记录，查询状态。初始化确定工作台身份和存储位置；项目登记让任务知道属于谁；创建任务固定需求；追加记录保留检查历史；查询把关联的数据重新组织给接手人。

保存还要保护数据关系。重复任务编号应在写入前被拒绝；不存在的任务不能接受记录。若一项操作需要写入多处，可以用**事务**保证它们一起成功或一起撤销，避免“报错了，却留下半条记录”。事务解决一次写入的完整性，重启查询解决持久性，两者需要分别验证。

从参考实现 [`workbench/bootstrap.py`](../../../workbench/bootstrap.py) 读取 `create_task()`、`add_evidence()` 和 `status()`，可以看到需求副本、证据追加和关联查询的职责。对照自己的程序时，重点是同样的行为有没有成立，函数名可以不同。

## 5｜从验收项长出测试，再解释红灯和绿灯

测试不是实现结束后补的一句“能运行”。它应先根据 Spec 写出输入、操作和预期，再让实现接受检查。沿用任务 A，先准备独立数据目录，创建任务并追加一条失败记录；结束进程，修改外部需求文件；启动新进程，读回任务与记录。需求应仍是创建时的副本，失败的命令、输出和退出码应原样保留。

这项测试同时反驳两种错误方案：只存在内存里，重启会丢；只保存文件路径，修改原文件后历史会变。用同一任务编号重复创建不同内容，则反驳覆盖旧任务的方案。这样，测试能解释“为什么这套检查抓得住错误”。

实现前目标能力缺失，测试失败，称为**红灯**；在授权范围实现后，同一测试通过，称为**绿灯**。红灯必须指向缺失行为。如果解释器未找到、参数拼错或用例没有运行，先排查环境。若改前已经通过，就调查已有能力并如实记录，不能补写失败。

### 同一条命令，为什么可能检查了不同的要求

再把“同一测试”推深一步。实现前，测试创建任务 A，退出进程，再启动进程，逐项比较原需求与失败记录。它失败后，Codex 有两条可能的改法：补齐保存与读回，或者把断言改成“数据库文件存在”。后一种改法也能让下面这条命令返回绿灯，甚至仍显示相同的用例数量，但它已经不再检查原来的要求：

```text
python -X utf8 -m unittest tests.test_l01_workbench_bootstrap -v
```

区别不在命令拼写，而在**这条命令此刻读到了哪份测试、测试实际比较什么**。“文件存在”不能推出“新进程能找回原需求”，正如一个空账本不能证明昨天的记录仍在。删掉重启步骤、把预期值改成程序实际返回值、给失败用例加跳过条件，都可能保留熟悉的命令而换掉验收标准。

| 实现前红灯与实现后绿灯怎样配对 | 可以作出的判断 |
|---|---|
| 测试快照相同；原断言运行；实现补齐保存与读回 | 原要求由缺失转为满足，仍需审查实现范围 |
| 命令相同；断言缩为文件存在 | 只能证明较弱的新检查通过，不能接受原要求 |
| 测试确需修订，且修订理由已经确认 | 为修订后的标准重新建立红灯与绿灯，旧记录保留 |

![从验收项、测试快照到同标准红绿结果](assets/reading-depth-20261003/mechanism.svg)

**图 1-2a　红绿结果之间必须保住验收标准。**这是教学机制示意，不是某次学生运行记录。上方沿“原要求—确认测试—有效红灯—同标准绿灯”阅读；反例说明，换弱断言可以让命令变绿，却无法跨过最后的完成判断。[可编辑源图](assets/reading-depth-20261003/mechanism.drawio)。

读图时先遮住绿灯，只看确认测试：它能否排除内存保存和只存路径这两种错误方案？再打开绿灯，对照实现前测试快照，检查断言、测试发现范围与跳过条件。手册第 3 步保存测试原样副本和 SHA-256，第 5 步比较当前版本，正是为了回答这个问题。内容标识可帮助发现变化，但它不能证明测试设计充分，也不能认证执行者身份。

参考账本 `BootstrapLedger._chain()` 会比较红绿命令和观察时间，并要求中间有 Diff；它不会替你审查测试断言有没有被削弱。因此 `evidence_complete` 是材料关系的检查结果，你还必须回到测试与原始输出作判断。迁移到“文档校对”时，同样要锁定校对依据和检查范围：若把“不得漏改指定错误”换成“文档能打开”，新绿灯便不再支持原任务。

## 6｜把绿灯放回实际改动中判断

通过后再看 **Diff，也就是修改前后的代码差异**。确认没有通过删除检查、放宽预期或修改无关目录换取绿灯。至少检查重启查回、需求快照、重复编号、不存在任务、缺少证据这几类情况；拒绝后还要重新查数据，确认原状态不变。

出现问题时，按观察定位：创建成功但重启查不到，核对数据目录和提交保存；能查到但需求变了，检查是否只存路径；重复编号报错却改了原任务，检查校验和写入顺序。不要仅凭最后一行“失败”猜原因。

## 7｜工作台怎样记录自己的建设

工具尚未建成时，先按[实践操作手册](实践操作手册.md)用采集工具保存真实命令与输出。建成后，在新工作台中登记“个人研发工作台”项目，创建“开发 V0.1”任务，把实现前失败、实际 Diff、实现后通过关联进去。这叫**自举**：新工具开始承担它自己的建设记录。

![用新工作台保存自身建设记录的步骤](assets/technical/06-bootstrap-flow.png)

**图 1-3　先采集，再建任务并导入证据。**图中的红灯、Diff 和绿灯是步骤示意。导入后查询应能找回原要求和前后结果；实际内容由你的执行产生。

这里有两个不同退出码。例如，先前的测试退出 1，表示那次检查失败；今天“追加记录”退出 0，表示这条失败记录保存成功。保存成功不能改变先前的失败事实。同理，`evidence_complete` 说明材料满足完整性条件，`acceptance` 仍可为待人工审核。人还需核对失败原因、改动范围和复验结果。

### 从证据优先，走向下一次能够改进的交付

如果第二天发现“重启后任务查不到”，只留下“昨天已经做好”的摘要，就无法判断昨天检查了什么。**证据优先**的意思是，先保存能够支持判断的原始材料，再形成结论：需求快照说明当时承诺什么，Diff 说明实际改变什么，命令与输出说明检查发生了什么，具名决定说明谁依据这些材料接受。结论可以简短，但接手人应能沿它回到原始材料，发现依据不足时重新检查。

这也是**可追溯交付**的关键。任务编号把材料关联起来，却不能自行证明内容真实；哈希帮助发现内容变化，却不能证明命令由谁运行。参考 `add_evidence()` 明确返回 `user_supplied_observation`，表示这是用户导入的观察。若把一份编造输出存进数据库，存储本身仍可能成功。因此完成判断要同时问“记录是否保存”“记录支持什么事实”，不能让保存动作替代对内容的核验。

将这个问题放回 FDE 三循环，关系就更清楚了。**现场循环**先查第二天接手为何困难：丢的是需求、输出，还是数据目录？**交付循环**把确认的问题变成受控改动，用新进程查回验证行为，再由人决定是否接受。**能力循环**从真实失败提炼下次可用的办法，例如“持久化验收必须跨进程，并明确同一个数据目录”；以后另一项保存任务采用它，还要用那项任务自己的结果检验。三个循环分别改变问题认识、可运行结果和可复用方法。

![人的判断、Codex 实现、工作台组织与客户反馈形成交付循环](../assets/advanced-concepts-20261003/01-delivery-cycle.png)

**图 1-4　证据怎样支持下一次交付。**这是全课程关系的教学示意。L01 位于建设工作台的阶段；图中的 FlowERP 交付从 L04 才开始。沿“人的决定—Codex 行动—工作台证据—客户结果—反馈”阅读，反馈需要回到实际问题和下一次决定。

读图时试着删去“证据”这一步：客户说任务又丢了，你还能查明哪版、哪个目录、哪条检查曾经通过吗？再删去人的决定：程序绿灯是否足以代表客户接受？两处缺口解释了为何自动化必须保留可回查材料与责任人。失败定位也沿这条链进行：需求理解错就回访用途，保存错就查实现，检查读错目录就修检查，材料不全就补采实际观察。

L01 建成的账本只是后续可信经验的原料，还没有完成记忆召回或工作流蒸馏。以后提炼经验时，要附来源、适用条件和失效条件；旧任务成功不能保证新情境成功。迁移到文档校对，可以复用“保留修改前版本和原始检查”，却要重新确认校对依据。下一项任务能说明采用了哪条经验、为何适用、复验怎样，才开始形成跨事项的能力增长。

## 8｜现在去实践，并判断自己是否掌握

打开[实践操作手册](实践操作手册.md)，从准备隔离练习区开始，按需求访谈、测试、实现、复验、自举的顺序行动。个人记录放在 `lesson-01-submission/`。你需要留下自己的取舍、实际红灯、范围内 Diff、绿灯以及查询自举任务的结果；完成要求见[手册中的目标与通过要求](实践操作手册.md#lesson-goals)。

请同伴只看你的 Spec，说明他会比较哪些值。如果他只能说“应该成功”，就继续细化验收项。如果他能指出重启、原需求副本、失败记录和拒绝后状态，再让他补查一项遗漏，保留反馈与修订。

迁移时换成“文档校对”项目：项目、任务、运行记录仍能沿用，任务快照应改为本次校对依据，验收应检查原文引用和修改范围。能重新选择要保存的内容和检查方式，说明你掌握了方法。工作台参考程序能运行，不能替代这一判断。

本讲应留下可运行的记录工具和本人的建设证据。下一讲继续用它，但还要让下一次 Codex 会话遵守同样的约定，于是把长期规则写入 `AGENTS.md`。

## 课程大纲中的本讲要求

- **核心内容**：开课时没有个人工作台、`WORKBENCH_SPEC.md` 或验收测试；学生从一句模糊诉求和真实痛点出发，利用 Codex 完成需求访谈，由学生决定范围并签署首份 Spec，再把验收项转成红灯测试，开发初始化、项目登记、任务账、命令证据账和状态检查。
- **演示结果**：`“帮我搭建个人 AI 研发工作台”` 经历“原始诉求 → Codex 追问 → 学生取舍 → `WORKBENCH_SPEC.md` → 验收测试红灯 → Codex 实现 → 同一测试绿灯”，最后由新工作台记录自己的建设证据。
- **课内增量**：学生亲手形成并签署首份 `WORKBENCH_SPEC.md`、从验收项生成失败测试、开发出可运行的 Workbench V0.1，并完成第一次自举记录；本讲不接入、不开发 FlowERP。
- **通过标准**：Spec 每项关键要求能回指原始痛点、Codex 建议和学生决定；测试能回指验收项；必须保留实现前红灯、范围内 Diff 和实现后绿灯；学生能用自己开发的命令完成自举，并说明 L04 才会通过“个人工作台 + Codex”开发 FlowERP。
