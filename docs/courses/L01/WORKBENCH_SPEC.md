# Workbench V0.1 需求说明书

> **文件性质：课程教学参考，未签署。** 本文件供阅读 L01 PPT 时打开对照，说明第一版工作台应做什么、怎样检查。它不代表任何学员已经访谈、作出决定、完成实现或通过验收。学员在自己的隔离练习目录中形成同名文件，保留个人决定来源并自行确认。

## 1. 来源与目标

需求来源是 L01 课程建设任务：“帮我搭建个人 AI 研发工作台”。使用者是组织自己与 Codex 协作的开发者。第一版解决一个具体问题：开发结束后，能够查回某个任务当时依据的需求、执行过的命令及其原始结果，而不用翻找零散聊天。

本讲交付 Python 命令行工作台 V0.1，提供初始化、项目登记、任务创建、运行记录追加和状态查询五个操作。完成后，用它登记工作台自身，保存自己的建设记录。课程最终通过工作台持续开发 FlowERP，首次接入客户项目在 L04。

## 2. 本次不做什么

- 不自动调用 Codex，不自动执行命令。记录由人使用课程工具采集后明确导入。
- 不自动决定需求是否合理、测试是否充分、代码是否值得接受。
- 不提供人工验收自动通过功能。材料完整后仍显示等待人工审核。
- 不在 L01 开发 FlowERP 库存、采购或其他业务功能，也不建设完整网页驾驶舱。

## 3. 一次使用流程与分工

1. 学员说明真实问题，Codex 协助追问和整理，学员确认需求范围与验收项。
2. 学员监督 Codex 编写验收测试，实际运行并保存有效的实现前失败。
3. 学员确认实现计划，Codex 修改允许范围内的代码，再运行同一测试。
4. 工作台初始化后登记“个人工作台”项目，为这次建设创建任务，保存需求与原始问题的快照。
5. 学员选择真实失败、代码改动和修复后输出，逐条追加到该任务。
6. 工作台查询并检查记录完整性。学员和复核者继续核对失败原因、改动范围与需求，留下自己的结论。

## 4. 保存哪些对象

| 对象 | 最小内容 | 关联与保存要求 |
| --- | --- | --- |
| 工作台 | 所有者、编号、名称、版本 | 初始化后持久保存，不能被另一个所有者覆盖 |
| 项目 | 项目编号、名称、代码路径、用途 | 任务必须属于已登记项目 |
| 任务 | 任务编号、项目编号、标题或请求、需求编号、创建人 | 同编号任务不得覆盖原任务 |
| 需求与问题快照 | 创建任务时的需求全文、需求摘要、原始问题全文 | 原文件后来变化，不应改写旧任务保存的内容 |
| 运行记录 | 阶段、原始命令、完整输出、返回码、带时区的观察时间、记录时间 | 关联任务，追加保存，保留输出摘要用于核对内容 |

这里的“摘要”是内容的 SHA-256 校验值，用来发现保存内容是否变化，不证明作者身份或观察时间真实。

## 5. 五个命令的输入与结果

以下子命令都通过 `python -X utf8 -m workbench.cli` 调用。实际运行前启用项目 `.venv`，并进入自己的练习仓库。所有命令使用同一个 `--runtime-dir .runtime/course/L01-workbench`。

| 子命令 | 主要输入 | 正常结果 | 错误或失败后的要求 |
| --- | --- | --- | --- |
| `workbench-init` | `--owner`，可选 `--name` | 创建工作台并返回身份、所有者、V0.1 版本 | 不用另一个所有者覆盖既有工作台 |
| `workbench-project-add` | `--project-id`、`--name`，可选 `--path`、`--purpose` | 保存项目，返回项目编号与名称 | 缺少必填输入或重复编号时明确失败，不覆盖旧项目 |
| `workbench-task-create` | `--project-id`、任务编号、`--title` 或 `--request`、`--spec-file`；可附原始问题、创建人与需求编号 | 保存任务和需求、问题快照，返回任务编号与需求摘要 | 项目不存在、编号重复或需求不可读取时失败，不改写原任务 |
| `workbench-evidence-add` | `--task-id`、`--phase`、`--command-text`、`--output-file`、`--returncode`、`--observed-at` | 追加运行记录，返回记录编号与输出摘要 | 任务不存在、时间缺少时区、输出不可读取或为空时失败，旧记录保留 |
| `workbench-status` | 可选 `--require-project`、`--require-task`、`--require-red-green-evidence` | 查询项目、任务及运行记录，返回完整性结果、问题列表和待人审状态 | 尚未初始化或要求的对象不存在时明确失败，不靠查询偷偷创建数据 |

阶段名 `red`、`diff`、`green`、`observation` 用于区分记录用途，不能代替实际结果。例如标为 `red` 的运行只有在失败原因有效且真实返回码非零时，才能用于证明目标能力缺失。

完整命令与参数以项目 [工作台命令入口](../../../workbench/bootstrap.py) 为准，逐步操作见[实践操作手册](实践操作手册.md)。

## 6. 完整性检查与人工审核

要求红灯、改动、绿灯记录时，应能找到先失败、后保存改动、再用同一测试命令成功的顺序。改动与最后成功记录的返回码应为零。后来再次失败时，不能继续用旧绿灯说明当前材料完整。

`evidence_complete: true` 表示记录通过了程序的完整性检查。`acceptance: pending_human_review` 表示仍然等待人工核对。程序不能由前者推断人工已接受，也不能认证导入命令的执行者、时间、失败原因或测试充分性。

## 7. 数据与修改范围

- 工作台运行库保存在 `.runtime/course/L01-workbench/workbench.db`，与 FlowERP 的业务数据库分开。
- 默认实现文件为 `workbench/bootstrap.py` 和 `tests/test_l01_workbench_bootstrap.py`，CLI 接入位置参照 `workbench/cli.py`。扩大修改范围前先说明原因并由学员决定。
- 课程采集工具 `docs/courses/L01/tools/evidence.py` 与导入工具 `docs/courses/L01/tools/import_evidence.py` 已提供，作用分别为保存实际命令结果和导入明确选定的记录。
- 不删除失败输出，不修改返回码或时间来拼出成功。运行数据库、个人记录和敏感信息不作为公共课程示例提交。

## 8. 验收用例

下表是要执行的检查约定，**未填写实际结果**。正常路径与失败路径均需在自己的实现上验证。

| 编号 | 前提与操作 | 预期结果与失败后状态 |
| --- | --- | --- |
| WB-01 | 在新的独立运行目录初始化，再结束进程并查询 | 工作台身份和所有者仍可查，持久保存有效 |
| WB-02 | 登记个人工作台项目，创建任务并指定需求、问题文件 | 任务属于该项目，可查回任务内容及快照 |
| WB-03 | 使用不存在的项目编号创建任务 | 明确失败，不产生无所属项目的任务 |
| WB-04 | 已有任务后，以同编号提交不同内容 | 第二次失败，原任务与已有记录不变 |
| WB-05 | 创建任务后修改原需求文件或原输出文件 | 已保存的任务需求、已导入输出仍为当时的快照 |
| WB-06 | 任务缺少必要运行记录，要求检查红灯、改动与绿灯 | 完整性检查失败，说明缺失，保留任务与已有记录 |
| WB-07 | 使用同一测试命令，依次保存有效失败、Diff 和修复后成功 | 完整性检查可通过，人工审核仍为待审核 |
| WB-08 | 用不同测试命令的成功记录配对原失败 | 不能形成同一命令的失败到成功链，保留全部记录 |
| WB-09 | 将绿灯时间放在失败或 Diff 之前，或成功后又出现失败 | 不能用无效顺序或旧绿灯说明当前完整 |
| WB-10 | 查询不存在的任务，或在未初始化目录查询 | 明确失败，不创建工作台，不改写其他任务 |
| WB-11 | 补上真实缺失记录后重新查询 | 可恢复检查，旧失败仍可查，不删除失败来恢复 |
| WB-12 | 完成以上操作后检查数据目录与结果字段 | 工作台数据独立，`flowerp_connected` 为 false，本讲未写 ERP 业务数据 |

参考验收实现可在项目 [tests/test_l01_workbench_bootstrap.py](../../../tests/test_l01_workbench_bootstrap.py) 打开对照。它用于理解检查方法，不能替代学生自己的实现前失败、实际修改和实现后结果。
