# L03｜实践操作手册

**本讲任务：把“增加库存导出功能”写成可验收的 Spec，并让个人工作台能够读取它、拒绝结构错误。** Spec 就是本次需求合同，写清要做什么、哪些不做、怎样判断完成。

你沿用 L01 的个人工作台和 L02 的仓库规则，直接监督 Codex 澄清需求、制作模板、开发解析器。你负责业务决定和复核。FlowERP 本讲得到可交接的库存导出需求，导出功能留到后续实现。

按下面 8 步操作。每一步都说明文件、操作和完成标志。

| 步骤 | 做什么 | 留下什么 |
|---|---|---|
| 1 | 准备环境和文件 | 本次记录目录 |
| 2 | 回答需求问题，请 Codex 追问 | `decisions.md` |
| 3 | 填写六部分合同 | `FDE_SPEC.md` 初稿 |
| 4 | 审查、修订并确认 | 初稿、确认版、审查记录 |
| 5 | 提炼通用模板 | 模板、采购草稿 |
| 6 | 建设并接入解析器 | 代码差异、前后测试结果 |
| 7 | 检查正常输入和错误输入 | 实际输出、退出码、人工判断 |
| 8 | 迁移方法并交接 | 提交记录、合同版本与内容指纹 |

## 第一步：准备环境，创建两个文件

**操作位置：自己的课程练习仓库根目录。**

沿用前两讲已经核对的虚拟环境。若当前练习仓库有自己的 `.venv`，先激活：

Windows PowerShell：

```powershell
.\.venv\Scripts\Activate.ps1
```

macOS / Linux：

```bash
source .venv/bin/activate
```

如果沿用 L01 隔离区借用的参考环境，按[执行与排错说明](../../reference/实操手册执行与排错.md)恢复环境和隔离目录。环境尚未建立时，先完成 L00。

核对解释器和源码位置：

```bash
python -X utf8 -c "import sys, workbench; from pathlib import Path; print('Python:', sys.executable); print('当前目录:', Path.cwd()); print('源码:', workbench.__file__)"
```

Python 应来自选定的虚拟环境；当前目录和源码应属于本次练习区。确认后创建记录文件：

```bash
python -X utf8 -c "from pathlib import Path; p=Path('lesson-03-submission'); p.mkdir(exist_ok=True); (p/'decisions.md').touch(exist_ok=True); (p/'FDE_SPEC.md').touch(exist_ok=True); print(p.resolve())"
```

打开输出的目录。新建文件为空是正常的；重复运行不会覆盖已有内容。

- `decisions.md`：记下你最初怎么想、查到了什么、最后怎样决定。
- `FDE_SPEC.md`：把确认后的要求整理成合同，第三步再填。

**完成标志：** 环境路径正确，两个文件都能在编辑器中打开。

## 第二步：先写自己的判断，再请 Codex 追问

**填写文件：`lesson-03-submission/decisions.md`。**

复制下面的结构，填写自己的答案。暂时不知道就写“待确认”。

```markdown
# L03 库存导出：判断与决定

记录人：
日期：
业务确认人：（课堂扮演负责人时注明“角色练习”）

## 首次判断（后续补充，不覆盖原文）
- 谁使用导出结果：
- 拿结果作什么决定：
- 可用库存怎样计算：
- 需要哪些列，每一行代表什么：
- 多条记录怎样排序：
- 没有库存记录时输出什么：
- 写文件失败时，怎样处理半成品，哪些业务状态必须不变：

## 调查与决定（每个关键问题记一条）
- 问题：
- 查到的信息及来源：
- Codex 的追问或建议：
- 我的选择及理由：
- 实际确认人、日期和状态：
- 仍待确认的内容：
```

先独立填写“首次判断”，再把原始诉求和这份记录交给 Codex。可使用[澄清歧义并冻结合同提示词](prompts/01-澄清歧义并冻结合同.md)，先完成其中的调查与追问部分。

要求 Codex 对每个问题说明：**缺少什么信息、不确认会造成哪两种实现、去哪里查证或由谁决定。** 你逐项回应，把采用、修改或退回的理由写回记录。

例如：在库 8、预占 3 时，可用量为 5。但同一个商品分布在两个仓库时，应导出两行明细，还是汇总成一行？这需要根据使用目的确认，不能仅凭“导出库存”四个字推定。

每条关键信息注明属于“仓库事实、课堂假设、负责人决定、Codex 建议”中的哪一种。调查 FlowERP 时使用独立客户仓库，记录实际代码位置；教学样稿不能充当已查证的代码事实。

**完成标志：** 读者能看出你的首次判断、依据、取舍和未知项；关键业务口径有明确的确认状态。

## 第三步：把确认后的要求填进 Spec

**填写文件：`lesson-03-submission/FDE_SPEC.md`。**

先比较[库存导出 v1 样稿](examples/inventory-export-v1.md)与[v2 样稿](examples/inventory-export-v2.md)，看多仓反例怎样改变行粒度、排序和验收。再根据自己的决定填写以下结构；样稿用于参考。

```markdown
## 来源
写原始诉求、事实依据、决定记录的位置、确认人和确认状态。

## 目标
写谁使用结果、解决什么问题、本次交付什么。

## 非目标
写本轮明确不做的功能。

## 约束
写库存口径、只读要求、字段与排序等必须遵守的条件。

## 验收用例
逐条写：给定什么数据，执行什么操作，预期看到什么，哪些状态不变。

## 完成定义
写需要哪些证据、由谁接受，以及仍未解决时不能交接的条件。
```

**保留这六个二级标题及顺序，把提示文字替换成实际内容。** 这是本课程解析器采用的格式。

填写“验收用例”时，逐项核对：

| 情境 | 必须说清的结果 |
|---|---|
| 正常数量 | 在库 8、预占 3，得到可用量 5；再写一组不同数量 |
| 字段与顺序 | 明确 `sku,name,site,location,lot_id,on_hand,reserved,available` 八列的含义与顺序 |
| 多仓、多仓位、多批次 | 每一行代表什么，是否汇总，按哪些字段排序；相同排序键怎样处理 |
| 空库存 | 输出表头、空文件还是错误，并说明采用理由 |
| 特殊字符 | 中文、逗号、引号、换行经过 CSV 读取后能够还原 |
| 写出失败 | 明确报错；说明已有目标文件、半成品怎样处理 |
| 只读性 | 成功和失败后，库存及流水均不变；写明如何比较 |

区分两种范围：**产品非目标**说明库存导出不做什么；**本讲允许修改文件**说明这次只建设模板和解析器，在第六步约定。

“完成定义”也要分清阶段：L03 完成需求确认和结构检查，后续实现仍须运行上述业务验收并由人接受。

**完成标志：** 六部分都有实质内容，每条验收都能观察结果；关键未知项解决前，合同保持草稿状态。

## 第四步：找出歧义，保留修订前后版本

**处理文件：`FDE_SPEC.md`，记录写回 `decisions.md`。**

1. 在编辑器中将当前初稿另存为 `lesson-03-submission/FDE_SPEC-v1.md`。后续修订继续写入 `FDE_SPEC.md`；已有初稿时使用新的版本名，保留旧记录。
2. 请同伴只读 Spec，复述正常结果，并指出一句可能产生两种实现的话。没有同伴时先独立找反例，记录“待互评”。
3. 把原始需求、候选 Spec、项目规则及 [Spec 验收审查 Skill](skills/spec-acceptance-review/SKILL.md) 交给 Codex，要求按该 Skill 审查。
4. 保留未经改写的真实响应。它应包含“审查结论、依据、关键发现、下一步”，结论为“退回修改”“待负责人确认”或“确认版可用”。
5. 你判断建议是否成立，修订合同并记下理由。填写实际确认人、日期和版本；课堂角色确认要注明“角色练习”。

若原文已经覆盖反例，记录对应条目和判断依据即可。若审查漏判，保留漏判并由你说明退回理由。

**完成标志：** 初稿与当前版本都保留，关键修改有理由。只有关键口径已经确认，才把当前版本标为确认版；Codex 的审查建议不能代替负责人确认。

## 第五步：做一份可复用模板，起草采购需求

**编辑文件：`workbench/templates/SPEC_TEMPLATE.md`。**

1. 从库存 Spec 中提炼六个固定标题，每节留下“待填写什么”的提示。
2. 删除库存公式、仓位规则、本次人员等业务专属内容。
3. 用模板核对自己的库存 Spec，确认它符合相同结构。
4. 从同一模板起草“采购申请导出”，保存为 `lesson-03-submission/procurement-draft.md`。对象、状态、字段和权限尚不清楚时写“待确认”。

采购草稿用于最后的迁移练习，不必现在取得业务确认。

**完成标志：** 同一模板能承载库存、采购两种需求；采购稿没有照搬库存专属规则。

## 第六步：让 Codex 建设解析器，接回工作台

**目标文件：`workbench/spec.py` 和对应测试。** 使用[实现最小结构解析器提示词](prompts/02-实现最小结构解析器.md)，按下面顺序推进。

### 6.1 查清起点，约定接口

先只读查看解析模块、`workbench/cli.py` 和现有测试，确认实际调用路径：

```text
workbench.cli spec → load_spec(path) → parse_spec(text) → ParsedSpec.as_dict()
```

在 `decisions.md` 记录：能力尚未实现、已有函数但未接入，还是已有能力已通过测试。

约定成功时返回 `source、goal、non_goals、constraints、acceptance、done` 六字段，保留各节原文；失败时指出具体结构错误。解析只读，不改输入文件、不提交业务任务。

允许修改解析模块、对应测试和通用模板；确实缺少 CLI 接线时才修改 `workbench/cli.py`，并记录原因。保留现有模块的其他职责。

### 6.2 先写测试，再做最小实现

让 Codex 先写测试，你核对这些预期：

| 输入或行为 | 测试预期 |
|---|---|
| 六节完整且有内容 | 返回六字段，值与原文一致 |
| 缺章、空章、重复、乱序、未知二级标题 | 明确拒绝 |
| 代码围栏中的示例标题 | 当作正文，不干扰章节识别 |
| 代码围栏未闭合 | 明确拒绝 |
| UTF-8 文件读取、成功与失败 | 内容正确，输入文件哈希不变 |
| CLI 调用 | 实际使用本次解析器；正常退出 0，结构错误退出非 0 |

测试必须导入本次练习区的实际模块。先运行并保存结果，再做最小实现，重跑同一组测试。已有能力全绿就如实记录“参考能力复验”；有真实缺口时才补测试和修复。

如果你新建的测试文件是 `tests/test_student_spec.py`，确认文件已保存后运行：

```bash
python -X utf8 -m unittest tests.test_student_spec -v
```

该文件需要本步实际创建。若采用其他名称，替换命令中的模块名；当前参考仓库已有的测试入口是：

```bash
python -X utf8 -m unittest tests.test_spec_contract tests.test_spec_cli -v
```

### 6.3 核对接入，保存差异

沿 CLI 的 `spec` 分支查到 `load_spec` 和本次解析函数，记录文件位置。若先在独立练习模块实现，将它接回上述接口，再验证 CLI；不要保留两套各自运行的解析逻辑。

保存修改差异、实际测试命令、测试数量、前后输出和退出码。测试零条不能算通过。

**完成标志：** 测试验证了真实实现，CLI 已调用该实现，修改范围符合约定。

## 第七步：运行三种输入，分别判断结果

每次运行前先写预测，运行后保存实际输出和退出码。**退出码要紧接着查询：** PowerShell 输入 `$LASTEXITCODE`；macOS / Linux 输入 `echo $?`，中间不要执行其他命令。

### 7.1 完整合同：应返回六字段

```bash
python -X utf8 -m workbench.cli spec lesson-03-submission/FDE_SPEC.md
```

预期退出码为 0，六字段内容与原文一致。

### 7.2 缺项副本：应明确拒绝

先复制完整合同，创建故障文件：

```bash
python -X utf8 -c "from pathlib import Path; p=Path('lesson-03-submission'); text=(p/'FDE_SPEC.md').read_text(encoding='utf-8'); f=(p/'missing-section.md').open('x', encoding='utf-8'); f.write(text); f.close()"
```

打开 `missing-section.md`，只删除 `## 非目标` 及其正文，保留其余五节并保存。完整合同保持原样。副本已存在时，打开检查或另存新版本，不覆盖旧实验记录。

```bash
python -X utf8 -m workbench.cli spec lesson-03-submission/missing-section.md
```

当前参考入口预期报错：`Spec 校验失败：Spec 缺少必要章节：非目标`，退出码为 1。自己的实现也应明确定位缺项并返回非零退出码。

运行前后分别计算两个输入文件的内容指纹，保存输出并比较：

```bash
python -X utf8 -c "from pathlib import Path; import hashlib; p=Path('lesson-03-submission'); [print(n, hashlib.sha256((p/n).read_bytes()).hexdigest()) for n in ('FDE_SPEC.md','missing-section.md')]"
```

同一文件运行前后指纹应一致。缺项被拒绝说明解析器按预期工作；它与“解析器缺能力导致测试失败”要分别记录。

### 7.3 结构完整、公式错误：应由审查者退回

1. 将完整合同另存为 `lesson-03-submission/wrong-formula.md`。
2. 把可用量公式改为“可用量 = 在库量”，保留六节及其他内容。
3. 预测解析结果后运行：

```bash
python -X utf8 -m workbench.cli spec lesson-03-submission/wrong-formula.md
```

结构完整时，解析器应通过。再用第四步的 Skill 审查该副本，并由你指出：在库 8、预占 3，应得到 5，错误公式却得到 8，违反了哪条约束和验收项。保留实际响应；漏判时记录人工退回理由，修正副本后复验。

**完成标志：** 三种输入均有预测和实际记录。你能解释：解析器检查结构，人审检查业务含义，后续产品验收检查实现结果。通用解析器无需硬编码库存公式。

补充查看参考 Eval 的覆盖范围：

```bash
python -X utf8 -m eval.harness --suite blocking --case spec_contract_rejects_ambiguity
```

该报告用于对照已有用例，不能替代个人测试或证明自然语言需求已完全消除歧义。

## 第八步：迁移到采购场景，整理交接材料

**先检查第五步的 `procurement-draft.md`。** 独立指出对象、状态、字段、权限还缺什么，再用同一 Skill 审查，记录哪些结构可复用、哪些业务决定需要重新确认。

从同一个工作台入口读取采购草稿：

```bash
python -X utf8 -m workbench.cli spec lesson-03-submission/procurement-draft.md
```

若六节有效但仍含“待确认”，记录“结构通过，业务待确认”。

然后把[提交模板](SUBMISSION.md)复制到记录目录，填写实际结果；已有文件用路径引用，无需重写长报告。对照[行动卡](行动卡.md)检查：

- [ ] 首次判断、来源、取舍和实际确认记录齐全。
- [ ] 库存 Spec 初稿、确认版及关键修订理由可追溯。
- [ ] 通用模板、采购草稿和迁移判断已保存。
- [ ] 解析器修改差异、调用路径、真实测试结果已保存。
- [ ] 完整输入、坏输入、语义反例的实际结果已保存，输入未被解析命令改写。
- [ ] 同伴能复述数量口径、行粒度、空集和写失败要求；没有同伴则标记待互评。

最后记录确认版的路径、版本与 SHA256 内容指纹：

```bash
python -X utf8 -c "from pathlib import Path; import hashlib; p=Path('lesson-03-submission/FDE_SPEC.md'); print(p.resolve()); print(hashlib.sha256(p.read_bytes()).hexdigest())"
```

核对实际解析文件与交接文件的指纹一致。若口径或内容再次变化，需要重新审查、确认并更新指纹。

**交给 L04：确认版库存 Spec、可复用模板、已接入的解析器和真实复验证据。** 库存导出功能的实现与业务验收仍待后续完成。

## 遇到问题时查这里

| 现象 | 下一步 |
|---|---|
| 找不到输入文件 | 核对仓库根目录，以及第一、三步是否已创建并保存合同 |
| 提示 `invalid choice: 'spec'` | 检查第六步的 CLI 接入是否完成 |
| 提示缺章、空章或错序 | 对照第三步的六个二级标题，检查名称、内容与顺序 |
| 故障副本提示 `FileExistsError` | 打开已有副本检查；需重做时另存新版本 |
| 正常合同意外失败 | 检查额外二级标题、代码围栏是否闭合 |
| 测试全绿，坏输入却通过 | 检查测试导入的模块和 CLI 实际调用路径是否一致 |
| 字段齐全，业务含义却错误 | 回到决定记录和业务反例，由人审查、修订 |

环境与编码问题见[执行与排错说明](../../reference/实操手册执行与排错.md)；概念与设计理由见[阅读讲义](阅读讲义.md)。
