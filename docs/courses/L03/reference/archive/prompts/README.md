# L03 分步 Prompt｜把工作台的需求入口建出来

L01 曾经靠人手写出第一份 Spec；L03 要把这次性的做法变成工作台组件。三份 Prompt 共同完成下面这条链路：

```text
业务原话
  → 人与 Codex 澄清并记录决定
  → 六部分确认版 Spec
  → workbench.spec 解析与拒绝
  → workbench.cli spec 统一入口
  → 交接包保留同一份确认、解析和复验过的合同
```

因此，本讲不是单独练习“怎么写 Markdown”或“怎么写解析器”。它在建设个人工作台的**需求入口与合同闸门**：后续任务只有拿到结构有效、版本明确、由人确认的 Spec，才具备进入受控执行阶段的前提。

## 三步分别给工作台增加什么

| Prompt | 工作台项目增量 | 必须留下的证据 | 完成状态 |
|---|---|---|---|
| [01 定义需求入口的合同](01-澄清歧义并冻结合同.md) | 把对话结果固定为统一模板、确认版 Spec 和决定记录 | 原话、关键追问、实际决定、Spec 修订 Diff、模板复用结果 | `contract_ready` |
| [02 建设工作台的合同闸门](02-实现最小结构解析器.md) | 让 `workbench.spec` 与 `workbench.cli spec` 能读取完整合同并拒绝残缺合同 | 单元测试、CLI 集成测试、前后结果、调用路径、输入未改变 | `gateway_connected` |
| [03 验收需求入口并准备交接](03-结构与语义复验.md) | 证明结构检查、业务审查和交接包指向同一份合同 | 正常/错误输入、语义反例、确认版路径、版本与哈希 | `handoff_ready` |

这三个状态只描述 L03 的建设进度，不是工作台运行状态枚举，也不代表库存导出已实现。

## 使用规则

每个编号文件只保留一段可以整体复制给 Codex 的 Prompt；学习目标、学员验收和提交要求分别放在本 README、行动卡、实践操作手册与提交模板中，不混进 Prompt 正文。

1. 先在实践操作手册中写自己的首次判断，再逐步使用 Prompt；不要一次性让 Codex 代写全部学习记录。
2. 每一步先读取真实仓库，再决定是否修改。参考终态已经具备能力时，保留事实；不要删除功能来制造红灯。
3. 学员决定业务口径、修改范围和是否采用建议。Codex 负责调查、起草、实现候选与报告证据，不能替学员签字确认。
4. 调查、Spec、实现、测试和交接引用同一份确认版合同。口径改变时生成新版本并重新确认，不能静默覆盖。
5. L03 只建设需求入口，不执行库存导出、不修改 FlowERP 业务代码，也不声称 Harness、Eval 或完整工作台 V0 已建成。

审查候选 Spec 时采用 Spec 验收审查 skill。skill 是可复用审查流程，仍须保留学员本人对建议的采用、修订或退回决定。
