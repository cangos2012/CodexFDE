# L03｜把模糊需求变成可验收 Spec

本卡用于实践时核对。具体步骤与命令见实践操作手册，判断理由见辅导资料。

## 本讲要完成什么

把“增加库存导出功能”变成一份来源明确、范围清楚、可以检查的六部分 Spec，并让个人工作台能够读取完整合同、拒绝结构错误的合同。

本讲建设的是工作台的需求入口。Codex 协助调查、起草和实现候选；你决定业务口径、是否采用建议以及能否确认；FlowERP 本讲只得到准备交接的需求，不实现库存导出。

## 按顺序核对

| 步骤 | 你要完成什么 | 应当看到的证据 |
|---|---|---|
| 1. 先判断 | 写下使用者、用途、库存口径和未知项，再请 Codex 追问 | 首次判断与后续决定分开保存；模型建议没有冒充人员决定 |
| 2. 写 Spec | 依次填写来源、目标、非目标、约束、验收用例、完成定义 | 正常、失败和边界情境都有可观察结果；只读操作写明什么必须保持不变 |
| 3. 做审查 | 使用 Spec 验收审查 skill 找出歧义和越界内容，再由你决定是否采用建议 | 保留关键反例、修订理由、待确认项和本次确认版；课堂角色确认须注明 |
| 4. 做模板 | 从确认过程提炼六部分模板，再起草采购申请导出草稿 | 两份需求结构相同；采购草稿没有照搬库存公式和仓位规则 |
| 5. 建入口 | 让自己的解析实现接入工作台真实入口 | 完整合同返回六字段；缺项、空项、重复、错序和未知标题被明确拒绝 |
| 6. 分层复验 | 分别检查结构错误和业务含义错误 | 结构错误由程序拒绝；结构完整但公式错误的合同由人用反例退回 |
| 7. 准备交接 | 核对确认版、实际解析文件和交接包中的文件 | 路径、版本和 SHA256 内容指纹一致；未完成的产品结果明确写为未验证 |

## 三条边界不能混淆

- 解析成功只证明六部分结构可读取，不证明库存公式正确。
- Skill 给出的结论是审查建议，不能替你或真实负责人确认需求。
- Spec、测试计划或参考仓库通过，都不能证明库存 CSV 已经实现和验收。

## 提交时只保留这些材料

- 本人的首次判断、关键决定及其来源；
- Spec 初稿、本次确认版和一项关键修订理由；
- 模板与采购申请草稿；
- 正常输入、错误输入的实际命令、输出和退出码；
- 解析器修改位置、代码差异，以及同伴反馈；没有同伴时如实写“待互评”。

材料引用已有文件，不重复写成长报告，不补造失败、确认或验收记录。

## 完成后应能回答

1. 为什么导出的可用量不是简单照抄在库量？依据来自哪里？
2. 怎样证明工作台真实入口调用了自己的解析实现，并能拒绝残缺合同？
3. 换成采购申请导出时，哪些结构可以复用，哪些业务决定必须重新确认？

这些合同与解析证据将在下一讲进入受控执行，但下一讲的实现结果需要重新验证。


## 大纲四项合同

以下逐项引用现行课程大纲，正文示例不替代当讲通过标准。

- **核心内容**：目标与非目标、正常与错误路径、边界条件、可执行验收项、最小变更原则。
- **演示结果**：把“增加导出功能”拆成结构化 `FDE_SPEC.md`。
- **课内增量**：由学生在外循环直接监督 Codex 实现 Spec 模板与最小解析器，只生成和校验合同结构，不执行 FlowERP 业务编码。
- **通过标准**：Spec 至少包含目标、非目标、约束、验收用例和来源；缺失必要字段时返回明确错误。
