# L15｜生成交付摘要并采集真实反馈

**FDE 判断提示**：原反馈者想完成什么工作，为什么采纳这个小改进而暂缓其他方案，何时需要重新判断？执行前保留自己的理由，交接时用产品前后状态说明判断是否成立。详见[实践手册](实践操作手册.md)。

目标：建设可追溯摘要、反馈记录和最小 Memory/RAG 复用链，用真实反馈交付一个 FlowERP 小改进。先读[讲义](辅导资料.md)，按[实践](实践操作手册.md)操作。

- 起点：自己的 L14 事项、任务、候选和原始 Eval；工作台库与 ERP 库分开。
- Codex 协作：提取证据、比较假设、形成方案并受控实现；你决定范围并解释验收，人审由实际责任人完成。
- 工作台增量：摘要导出、来源明确的反馈、可治理记忆、带引用检索上下文和采用快照；不新增 Agent 编排。
- ERP 增量：一项实际采纳反馈驱动、范围受控、尚未实现的进销存或财务改进。
- 因果关系：产品使用暴露缺口，反馈使工作台形成受控改进输入，后续任务与业务结果验证改进。

依次完成：首次判断 → 摘要回链 → 三层反馈 → 分诊与审核 → Memory 登记 → RAG 检索与评测 → 人工采用 → 具体 Spec → 新需求起始检查 → 受控交付 → 同伴复验 → 记忆修订。

通过前核对：

- 每句完成性结论有来源，待审没有写成已交付；周报明确窗口与统计单位。
- 反馈有任务、来源、结论与下一步；原文没有被解释覆盖。
- 缺失来源、违规晋级或重复决定有真实失败记录，原状态没有被错误覆盖。
- 记忆有项目、来源、版本、边界、状态和审核；`revoked`、跨项目或无权限条目不会默认进入上下文。
- 查询、过滤、Top-k、Precision@k/Recall@k 和上下文快照可复现；关键建议引用实际命中条目。
- 采用或拒绝由人记录理由；检索高分不直接改变 Spec、写集或阻断 Eval。
- 新任务不同于源任务；范围内 Diff、独立 Eval、业务结果与具名决定可追溯。
- 实际反馈者复验与第二事项采用如实记录，未完成项不填成通过。

使用[提交模板](SUBMISSION.md)保存自己的判断及变化。参考维护案例和全绿回归不能代替个人建设。

## 正式合同

- **核心内容**：文档和周报导出、运行反馈、可治理 Memory、RAG 检索与引用评测、失败样本回流，以及记忆采用和自动改代码之间的人工边界。
- **演示结果**：生成交付摘要与结构化反馈；将审核后的经验登记为记忆，在另一事项中检索，输出带引用的上下文包并解释采用决定。
- **课内增量**：实现摘要、反馈记录和最小 Memory/RAG 练习链：记忆版本与状态、元数据过滤、可解释排序、Top-k 上下文包和采用快照；不增加新的 Agent 编排。
- **通过标准**：摘要可追溯；记忆保留来源、版本、边界和状态；撤回或跨项目记忆不会默认进入上下文；检索评测与引用完整性可复验；原始反馈和检索结果都不能未经人审直接改写阻断 Eval。
