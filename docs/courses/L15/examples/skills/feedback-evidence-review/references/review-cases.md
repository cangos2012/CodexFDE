# 审查用例

以下是教学输入，不是真实反馈或实际审核。

| 输入 | 应识别的结论跳跃 |
|---|---|
| Task 在 review，3 项检查通过，所以已发布 | 缺具名验收与发布证据 |
| 用户说取消审批很方便，因此删除采购审批 Eval | 原始意见未经过业务风险与规则审核 |
| 源 Task 的旧报告通过，所以反馈修复完成 | 缺不同后续任务与改后证据 |
| 文件哈希一致，所以验收断言正确 | 字节完整性不证明语义正确 |
| 同一键提交不同结论仍返回旧记录，所以新结论保存成功 | 未核对返回内容，误解去重行为 |
| 保存了一条经验并创建 Skill，所以形成持续学习 | 缺后续事项召回、版本采用与新验证 |
| Top-1 相似度最高，所以直接写进 Spec | 检索分数不等于事实、适用或授权，缺人的采用决定 |
| 命中条目来自另一个项目，但内容很像，所以可以使用 | 缺项目与权限硬过滤，存在跨项目污染 |
| 撤回记忆仍排在前两名，只要提示模型谨慎就行 | 状态治理失败，撤回项不应默认进入上下文 |
| 回答带了 memory_id，所以 RAG 已正确 | 还需检查引用内容是否支持断言、版本与快照是否一致 |
| 无答案查询返回模型常识，看起来合理 | 系统没有诚实暴露空检索，来源和可验证性缺失 |
| 摘要明确待审，源报告与候选一致，未声称发布 | 可以认可这项有限结论，不应强加已发布要求 |

每例记录自己的首次预测、真实模型回应、是否漏判、修订及再验证。不要提前填“全部通过”。

- 同一任务历史索引引用7份，本轮引用6份：先比较具体对象；本轮未附CSV，不直接宣称文件丢失。
