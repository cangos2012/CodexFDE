# 反馈与交付证据审查

适用于学生提交的摘要、反馈分诊、Spec/Eval 候选和后续验证包。只作审查建议，不写入审核决定，不自动改规则或代码。

1. 确认来源事项、源 Task、反馈 ID、需求版本、候选和后续 Task。缺失时说明影响，不能编造关联。
2. 将原始观察、工程解释、人的决定分开；引用原话，不润色覆盖。
3. 逐条检查摘要结论是否有相应粒度的证据，区分请求成功、检查通过、具名验收、发布与业务效果。
4. 检查反馈是否经审核，接受是否被错误扩大为直接改阻断规则；检查候选用例的前提、反例和适用边界。
5. 核对后续任务不同于源任务，实际修改与需求相关，报告和业务对象可追溯。已有绿报告不证明新改进。
6. 对 Memory 只认可项目、来源、版本、适用边界、状态和审核完整的条目；`candidate`、`superseded`、`revoked` 或跨项目条目不得被默认当作当前依据。
7. 对 RAG 核对查询、硬过滤、Top-k、相关项集合、Precision@k/Recall@k、上下文快照和 `memory_id@version` 引用；相似分数不证明正确，引用存在不证明支持。
8. 对采用和蒸馏只认可人的明确决定、实际执行和新验证；没有跨事项采用则标为候选或待验证，失败要定位并修订或停用。

面对运行记录时，先核对来源类型：当前执行、历史任务复核、同伴试用和实际客户反馈分别说明。读取历史 codex 任务不等于本轮再次调用模型；由截图推测的用户影响不等于已取得用户原话。

摘要的引用数按本次索引计算，检查新增或省略的具体对象，不能仅凭数量变化判断证据丢失。去重反馈应同时核对返回 ID 与正文；同键异内容返回旧记录时，将修订记为未保存，不得编造“已更新”或“冲突拒绝”。

为每个建议给出可复验条件：原对象、原输入、实际返回、失败后的状态，以及下一步由谁判断。单次治理分支拒绝只支持该路径，不证明所有入口均无法越权。

跨版本反馈先核对当前实现。历史离线旧状态已修复时，保留其原始描述与修复证据；后续发现退出焦点丢失，应关联为新观察，不覆盖旧反馈，也不照抄为当前仍有旧缺陷。当前会话直接修复与正式反馈采纳到独立后续Task分开判断；没有实际采用记录时，不能由两份课程材料互相引用推断闭环。

输出按“发现—原句或对象—缺失或冲突的证据—建议核对动作”组织。结论限定为当前提供材料，不能把结构检查当作真实权限、安全或学生能力证明。正常结论也要指出具体支持证据。

使用[审查反例](references/review-cases.md)先预测输出，再记录真实模型响应与漏判；本文件存在不证明 Skill 效果已验证。
