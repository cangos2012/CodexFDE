# L07｜用 Codex Hooks 建立本地护栏

**FDE 判断提示**：草稿订单交付中漏掉的是哪次检查，影响哪项销售判断，为什么选定这个触发时点？执行前保留自己的理由，交接时用产品前后状态说明判断是否成立。详见[实践手册](实践操作手册.md)。

**学习成果**：能从订单交付问题中诊断工作台缺口，选择改进位置，并用真实事件和最终复验解释改进的效果与边界。

**目标**：通过工作台交付草稿订单；将统一 Harness 接入项目生命周期，证明遗漏检查可以被发现和反馈。创建订单不预占库存，L08 再处理原子预占。

1. 阅读[讲义](辅导资料.md)，独立手算两行金额；按手册第 2.2 节核对最后一次修改、报告来源与当前显式检查，区分缺少断言、测错候选、执行故障和触发遗漏。先写改进决定，再选择事件。
2. 按[手册第 2～3 节](实践操作手册.md)运行真实订单实验与六类协议实验；再对照真实子进程失败、重入仍红及修复绿灯，分别记录能证明的范围。
3. 审查自己的配置、处理器、解释器与候选目录；补齐同入口调用、异常、超时和重入策略。提供个人 Diff 和针对个人模块的测试。
4. 通过 L04 接受的工作台提交 L07 实际编码，将 Hook 产物写入 `hook_staging/`；人工审查安装后验证事件，补足多行与失败后状态检查。
5. 在对应候选中取得真实 Hook 失败、续跑与恢复记录。最终显式复验不能由重入跳过代替。
6. 对照接入前后证据，分别判断触发是否有效、最终业务是否通过；请同伴复验并记录实际审核；用 skill 检查三个证据反例，完成副作用前选点的迁移练习。

建议线上精讲聚焦问题、事件和三层结果，控制在 30 分钟；其余实验、修订和同伴复验在行动课或课后完成。不要为赶时间省略真实事件项，未完成就如实保留。

**提交**：[SUBMISSION.md](SUBMISSION.md)承接首次判断、业务状态、原始协议、真实事件、个人修订和具名复核。零退出码、配置截图、模型自述不能单独证明通过。

- **核心内容**：生命周期 Hook、信任边界、超时、失败策略，以及 Hook 与 Git Hook 的区别。
- **演示结果**：Codex 在关键生命周期节点运行质量检查并反馈失败。
- **课内增量**：配置一个项目级质量 Hook，调用统一 Harness，而不是复制另一套质量逻辑。
- **通过标准**：Hook 来源可检查；故意引入违规时流程被阻断；恢复后重新通过。
