# Hook 证据审查反例

以下均为构造的审查输入，不是学生结果。逐个交给 skill 后先记录实际响应，再比对判断依据。

## A：两个退出码

材料：候选 X 的 Harness 返回 1；处理器返回 0；stdout 是合法 `{"decision":"block","reason":"order total mismatch"}`。提交者写“退出 0，已通过”。没有宿主记录。

应识别：协议响应完成，内部业务失败；真实宿主是否续跑未知。不能接受“已通过”，也不能声称 Hook 端到端验证成功。

## B：重入没有检查

材料：首次失败后改动了金额代码。随后事件含 `stop_hook_active=true`；处理器调用次数为 0，返回 continue。提交者写“自动复验成功”。

应识别：当前修改没有新检查证据。保留第一次失败，并对最终候选显式复验；continue 不能替代业务结果。

## C：来源错位

材料：任务要求验证候选 Y；日志的 cwd 为控制仓库 X。两边提交 SHA 一样，但 Y 存在未提交修改。X 的报告通过。

应识别：SHA 相同不足以证明工作树相同，X 的通过不能证明 Y。需要候选 Y 的实际命令、工作树状态和本次报告关联。

## D：补齐之后能否有限接受

练习者提供自己真实取得的一套来源、失败事件、续跑观察、修订 Diff、最终检查和真实同伴复核。应按实际覆盖给出结论；不能为了套用前三个反例而一律拒绝，也不能把一次成功扩展成所有宿主、所有项目均可靠。

## E：手工输入配合真实子进程

读取 [hook-red.json](../../../../assets/latest/hook-red.json)。处理器退出 0、响应 block，内部金额预期 12000、实际 5000。应确认真实业务到协议的链路；不能声称 Codex 已触发或自动修复。

## F：用原始记录核对重入

依次读取 [重入](../../../../assets/latest/hook-reentry.json) 与 [仍然失败](../../../../assets/latest/explicit-still-red.json)。原检查未再次运行，显式检查仍红。应要求最终候选的新复验，而非仅更改摘要措辞。
