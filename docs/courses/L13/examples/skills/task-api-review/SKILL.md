# 任务 API 审查

读取实际启动入口、接口处理函数、Spec、执行器、任务存储和原始实验材料。先确认服务表面与执行模式，不把同名路径或 executing 标签当作已执行开发。

## 跟踪一次提交

分别识别 HTTP 请求、研发任务和业务单据。检查提交前后的持久化时点，确认返回编号可查询，并区分 2xx、任务完成和业务结果。异步证据应表明响应不等待长任务结束，不能只依赖耗时猜测。

核对提交键的作用域、内容规范、保留规则和并发创建。观察同键重放、同键改内容、新键重复业务操作；不要用捕获冲突后换键掩盖重复。分别检查数据库记录、前置文件与外部副作用，事务不自动覆盖所有存储。

## 审查状态与决定

检查允许边、触发动作与对应权限；合法状态边不自动使每个入口的调用合法。报告应完整、有效并对应候选；非空姓名不证明身份。区分业务审批和研发交付审核，明确批准哪份版本。

检查 version 的实际增量与写入条件，不凭字段存在声称支持客户端并发比较。用竞争决定与过期候选检验守卫。区分当前失败与历史事件，保留真实失败，不用删日志修饰成功。

## 检查恢复与结果

区分重新打开存储、真实服务重启和执行中断恢复。查进程证据、原 Task ID、旧事件、报告和审核是否保留。已完成任务还应比较重启前后完整查询响应，核对旧服务已退出、新进程确实读取原运行目录；教学审核字段只能检验持久化，不能证明真实人审。对检查中断与修改中断分别判断能否重放，识别残留写入进程、已完成副作用和需要人工核对的情况。

把业务引用追到真实对象，并核对单据、数量和流水。引用存在或任务 completed 不能代替业务交付。教学实验与合成数据可验证机制，不证明学生本人达成或真实线上收益。

## 输出与流程复用

按已验证、与合同冲突、证据缺失给出结论，各项关联原始证据。不要代替人批准交付或删除失败现场。使用[反例](references/review-cases.md)观察审查是否漏判，保留真实回应与修订。

提炼复用流程时说明来源、适用条件、有效状态和版本；声称闭环必须检查后续事项实际召回与采用、Harness 和具名审核，以及失败如何触发修订或停用。
