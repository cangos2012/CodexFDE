# 审查反例

这些是审查输入，不是已经发生的交付或学生成绩。先预测再提交给 Skill，保留真实响应；漏判时修订并重试。

| 输入 | 应识别的问题 |
|---|---|
| POST 返回 202，页面显示“采购已入库” | 受理不能证明任务或业务完成 |
| GET 为 200，body.status 为 rework，调用方记为成功 | HTTP 与任务状态混淆 |
| Task ID 不同，但都是同一次超时重试创建 | 提交身份没有稳定复用 |
| 同键改 actor 返回冲突，文档却称按 actor 隔离 | 实际键作用域与协议不符 |
| tasks 表只有一行，目录多出三个无引用 Spec | 任务幂等不能证明文件无残留 |
| version 存在，审核不提交旧版本 | 尚未证明客户端乐观并发控制 |
| reviewer="张老师"，因此宣称已认证教师批准 | 身份字段与认证、真实决定混淆 |
| 重建 WorkbenchApp 后可读，所以声称服务中断恢复通过 | 缺真实进程中断和恢复证据 |
| 执行代码中断后直接自动再跑，未查残留进程 | 重放副作用与执行所有权不明 |
| 采购引用是占位符，任务通过，被当成真实 ERP 交付 | 未核对真实业务对象和结果 |
| 前一任务有总结、后一任务有报告，声称经验闭环 | 缺召回、采用理由、流程版本及本次复验 |

正向材料应包含：明确的任务合同；真实运行入口与执行模式；同一任务的受理、执行、失败和恢复证据；候选绑定的报告与人的决定；业务对账；后续采用及其边界。即使这些字段齐全，仍要打开来源判断真实性。
