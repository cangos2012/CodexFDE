# L13｜把执行链路封装成任务 API

**FDE 判断提示**：补货请求的提出者遇到了哪种重试或接续困难，为什么当前范围只需提交与查询两个接口？执行前保留自己的理由，交接时用产品前后状态说明判断是否成立。详见[实践手册](实践操作手册.md)。

目标：实现任务提交与状态查询两个最小接口，通过它们组织 FlowERP 补货交付。工作台新增稳定任务身份、异步受理、持久状态与证据查询；ERP 结果用真实采购、库存和流水验证。

1. 先区分业务问题、PRD、方案、任务执行和真实采购；写出 202、review、completed 的含义。
2. 运行[参考 HTTP 实验](examples/task_api_lab.py)，比较首次预测和真实报告。记录它没有执行 Codex、没有新增 ERP 功能的边界。
3. 完成[实践手册](实践操作手册.md)中的真实进程中断实验；在个人实现中补做完成任务的真实重启 HTTP 查询。
4. 制定小范围 Spec，包含提交键、状态边、失败语义、身份与审核对象；由 Codex 协助实现，保留真实起点与范围内 Diff。
5. 同一任务关联补货对象，完成真实候选复验与具名交付审核，再分别核对采购审批、入库和重放不重复。
6. 接受一次同伴反证，修订后复验；在下一需求采用有来源、有边界的流程版本，记录迁移结果。

本讲分别涉及工作台 Task API 与独立 FlowERP 补货服务。当前课程组合候选中的 `workbench/`、客户业务包 `flowerp/` 及按来源区分的 `eval/`、`tests/` 均以返回的候选目录为基准，不表示 CodexFDE 根目录含客户业务包；实际授权按本次 Spec 收敛。CLO6 的证据来自你的设计、实现、失败、修订、复验与迁移，而不是参考仓库通过。

正式合同：

- **核心内容**：任务模型、异步执行边界、状态机、持久化和最小权限。
- **演示结果**：提交任务后获得 ID，并查询 Spec、执行阶段和最终结果。
- **课内增量**：实现任务提交与状态查询两个最小接口。
- **通过标准**：状态只按合法路径变化；失败原因可查询；已完成任务在服务重启后仍可读取。

使用[提交模板](SUBMISSION.md)交接原 Task ID、候选与原始证据。若某项未完成，写明缺口，不把合成输入、字段姓名或重新打开数据库当作实际交付、人审或进程恢复。
