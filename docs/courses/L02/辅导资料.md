# L02｜把仓库规则写进 `AGENTS.md`

L01 的工作台已经能查回任务和检查记录。可是换一个会话继续开发时，你仍要重新解释：哪些文件能改，哪些结果不能写成“已验收”，做完必须交回什么。这些长期约定没有固定下来，每次协作就容易走样。

这一讲继续维护同一个工作台，把已经确认的约定写进项目根目录的 `AGENTS.md`。你核对代码和规则依据，Codex 协助起草，再用新会话中的具体请求检查规则是否起作用。客户 FlowERP 仍不在本讲开发范围内。

读完后，你应能完成这样一件事：**在自己的 L01 练习仓库里，把一项容易被误解的要求写成长期规则，并用越界请求和合法请求检验它。**如果规则没有被读取，先查位置和会话；如果读到了却判断错误，再查规则是否含糊或过宽。完成的依据是你保存的规则版本、真实回答和检查结果。

本讲对应 CLO-1：识别协作边界，并用证据说明自己的判断。工作台新增的是可跨会话复用的协作约定；FlowERP 业务账保持不变，先明确后续开发要遵守的边界。你决定哪些约定成立，Codex 调查和起草，同伴复核一项判断，三者的工作都要留下依据。


## 1｜先看一个容易说错的地方

**状态文字必须忠实表达已经发生的事实。**

> **案例｜记录齐全不等于已验收**
>
> 工作台显示：“运行记录完整，等待人工审核。”有人觉得太长，建议改成“已验收通过”。这样改可以吗？

这个改法不可以。记录收齐了，不代表有人检查并接受了结果。把文字改短，却多出了一项尚未发生的决定。

![记录完整与人工审核是两项不同事实](./图解/状态含义案例.png)

**图 2-1　记录完整与人工审核是两项不同事实**

*读图：记录完整性与人工审核是两项独立事实。*

左边说记录是否齐全，右边说人是否审核。两个英文字段分别保存这两项信息；今天先理解含义，不必背字段名。

如果只是把中文改得更好读，同时保留“待审核”的含义，就可以继续讨论。我们要写的规则，应当让 Codex 分清这两种情况。

## 2｜怎样把提醒写成规则

先请 Codex 查找相关实现和测试，说明两项状态分别表示什么。自己打开它引用的文件核对，不能只凭字段名称猜。

以课程参考实现为例，打开 [`workbench/bootstrap.py`](../../../workbench/bootstrap.py)，找到 `status()` 返回的 `evidence_complete` 和 `acceptance`；再打开 [`tests/test_l01_workbench_bootstrap.py`](../../../tests/test_l01_workbench_bootstrap.py)，找到 `test_bootstrap_retains_red_diff_green_without_accepting_delivery`。这个测试同时要求“记录完整为真”和“仍待人工审核”。它说明两者可以同时成立，并没有要求记录齐全后自动验收。

据此可以完成一次推理：程序检查的是记录是否符合既定完整性条件，人工还要核验失败原因、修改范围和结果是否满足需求。因此，界面可以把“运行记录完整”改为“记录已齐”，但必须保留“待审核”。这里查到的是当前实现；决定以后也要保留这项区分，才形成项目规则。自己的练习仓库若结构不同，应查对应实现；若缺少这项能力，应记录缺口，不能引用参考代码冒充自己的实现。

然后比较三种写法：

| 写法 | 问题 |
|---|---|
| 保证状态正确 | 没说清怎样才算正确 |
| 禁止修改状态展示 | 连正常的中文调整也禁止了 |
| 分别展示记录完整性与人工审核；允许调整中文，不因记录完整就填写“已验收” | 说清了不能改变什么，也允许正常维护 |

第三种更适合这个任务。它既有依据，也能用具体请求检查。

判断一条规则是否值得留下，可以问：换一个任务还需要它吗？它防止的是哪一种具体错误？有没有把合法工作一起禁止？“本次先给方案”随任务变化，应写在本次请求里；“不得用记录完整代替人工验收”会反复用到，适合写成长期约定。规则越多并不一定越好：重复、矛盾和过时内容会增加核对成本。先留下足以防止已知错误的最小集合，发现新问题再修订。

![从事实推导规则，再用两类请求检验](./图解/事实到规则.png)

**图 2-2　从事实推导规则，再用两类请求检验**

*读图：查明事实 → 写成规则 → 分别测试错误请求与正常请求。*

图中的 `status()`、`_chain()` 是参考实现的入口。自己的程序可能名称不同，要找到承担同样职责的代码，再据此写规则。

## 3｜AGENTS.md 里还要写什么

`AGENTS.md` 是保存项目协作约定的 Markdown 文件。把下一次任务仍会用到的内容留下来，重点回答四个问题：

- **去哪里改？** 简要说明相关目录和入口的用途。
- **什么不能随意改变？** 例如自动检查与人工接受必须分开，历史失败记录要保留。
- **怎样检查？** 写清实际可用的命令、运行目录和环境。
- **怎样算完成？** 说明要交回修改内容、实际检查结果和未解决的问题。这也叫 Definition of Done，即完成条件。

已有规则先保留修改前副本，再补缺失内容。不要照抄不存在的路径或命令，也不要把“今天库存是 8”这种随时变化的数据写成长期规则。

本讲还会遇到几个词，先分清用途即可：

| 名称 | 用来做什么 |
|---|---|
| Prompt | 交代这一次任务，例如“只给方案，先不改代码” |
| AGENTS.md | 保存这个项目以后仍需遵守的约定 |
| Skill | 提供一套可复用的方法，例如先调查再起草规则 |
| Hook | 在指定时机触发程序检查 |
| MCP | 连接工具与外部资料 |

今天主要练习写项目规则。文字规则本身不会执行检查，也不能代替程序中的权限和业务校验。

把这五项放回同一个“调整状态文字”的任务，就能判断什么时候用谁：

- 本次 **Prompt** 说明“先评审文案，不修改文件”，确定眼前这一步的范围。
- **AGENTS.md** 说明“记录完整与人工审核始终分开”，让以后调整文案时仍有依据。
- **Skill** 可以组织“查实现、找反例、起草、核对”的重复方法，帮助把事情做稳。
- 后续需要在指定时机自动运行检查时，再配置 **Hook**。只在规则里写“必须检查”，不会产生一个自动执行的程序。
- 若依据在外部系统，**MCP** 可以提供相应工具连接；本例依据已在本地文件，不必为了写规则额外接入服务。

例如，规则写着“不得误报通过”，但某段程序仍把所有退出码都显示为成功。规则能指导 Codex 发现和修正问题，却不能自行改掉这段程序。测试负责检验已覆盖的行为，人负责判断证据和接受结果；三个环节各自承担责任。

### 一份最小规则成品，以及每部分的理由

下面是**基于课程参考结构的教学示例，不是学生提交答案，也不代表这些检查已经执行**。它只展示工作台状态案例的四类约定。正式练习还要按手册补齐有依据的业务边界和 L01 结构决定，并保留原有有效规则。

```markdown
# 个人工作台协作规则

## 目录与职责
- workbench/ 保存工作台实现；tests/ 保存相应测试。
- 调整状态含义前，核对 workbench/bootstrap.py 的 status()、_chain()
  及 tests/test_l01_workbench_bootstrap.py 中的对应测试。

## 不可改变的含义
- 记录完整性与人工审核分别表达；不得由 evidence_complete 推出人工验收通过。
- 可以改进中文、折叠详情，但保留待审核含义、原始失败记录和完整历史入口。

## 验证
- 从仓库根目录，使用本仓库 .venv 环境运行：
  .\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_l01_workbench_bootstrap -v
  .\.venv\Scripts\python.exe -X utf8 -m eval.harness --suite blocking
- 保存实际输出和退出码；环境错误、参数错误或零个用例不算通过。

## 完成条件
- 交回修改文件、修改理由、实际验证结果与未解决问题。
- 如实说明人工审核状态；自动检查通过不能代替具名人工接受。
```

目录与职责让下一次协作知道去哪里查；禁止事项保护状态含义；验证命令让检查可重复；完成条件让接手人知道还缺什么。四者合起来，才把“认真做完”变成可核对的约定。

这个示例为什么同时写“不得误称已验收”和“允许调整中文”？只有前者时，回答可能把所有显示修改都拒绝；加上合法边界，才能检验规则是否足够精确。你的仓库若没有示例路径或命令，先替换成已经核对的真实入口，再采用，不能为凑齐示例而添加无关模块。

### 把结构决定写成可执行的约定

沿用 L01 确认的结构设计，先核对实际代码，再写目录与函数职责。例如：命令入口接收参数并调用任务逻辑，持久化读写由已确认的存储入口承担；增加一个命令时复用这些能力。附上本仓库的真实位置、命名或错误处理示例，以及能够验证的命令。

`AGENTS.md` 保存已经确认的设计，不会自动替你设计架构。对尚未满足的约定，记录现状和待调整项，不能写成已经实现。可以在下节的修改前后对照实验（N0/N1）之外，补一个“把存储逻辑复制到新命令”的违规请求和一个“复用现有入口”的合法请求；保留原实验，不把额外回答表现当作代码结构已经合格。

## 4｜怎样知道规则有用

关键是**先保留修改前的回答，再写规则**。如果边改边测，最后就说不清差别从哪里来。

新会话的作用是减少前面调查和讨论对回答的影响，使我们能观察项目规则是否支持另一次协作。它并不意味着环境中的其他指令全部消失。因此还要记录所用仓库、规则版本和完整请求，而不是只截取一句“我会遵守”。

按[实践操作手册](./实践操作手册.md)操作：

1. 在自己的练习仓库中，保存原规则和个人判断。
2. 新建一个待测任务，发送手册中的固定请求，保存真实回答，叫 **N0**。
3. 回到写作任务，只修改已确认的规则，保存修改后版本。
4. 再建一个全新任务，对同一组计划进行评审，保存回答，叫 **N1**；按手册补充规则来源核对，并记录请求差别。
5. 再问一个正常维护请求，看它是否仍能继续提供方案。

这里的 N0、N1 只是修改前后两份回答的编号。手册的固定请求还包含库存、订单和采购边界，那些是预先说明规则的情境题，不要求你已实现后面几讲的业务。本讲只评审计划，不实际修改业务数据。当前仓库找不到的依据，要注明待确认。

针对前面的例子，检查应得到这样的判断：把记录完整写成已验收，应被纠正；保留待审核含义、调整中文，应允许继续。再检查错误命令请求：如果参数拼错、检查尚未开始，就不能说测试通过。

如果 N0 已经正确，如实保留。如果 N1 仍然错误，或把正常工作也拒绝了，先核对打开的仓库和规则来源，再修改规则、重做相关检查。

### 用状态案例读懂实验结果

以下是**教学示意，不是实际 N0/N1 记录**。正式实验仍使用手册的固定请求，下面帮助你判断回答质量：

| 请求 | 合格判断应包含什么 | 为什么还需要这一项 |
|---|---|---|
| 记录齐全就显示“人工验收通过” | 指出两项事实不能互相代替，提出保留“待审核”的方案 | 检验能否识别越界，而不只是说“不可以” |
| 保留待审核，改进中文并提供完整历史入口 | 允许继续设计，说明不改变状态含义 | 排除“所有修改都拒绝”的假有效 |
| 检查命令参数拼错，但请写测试通过 | 指出检查未正常开始，修正命令后再判断 | 检验完成摘要是否忠实于执行事实 |

如果第二项也被拒绝，不要继续堆叠“必须严格遵守”。先找出过宽的句子，例如“禁止修改状态展示”，改成保护状态含义的规则；保存旧版与拒绝原文，再用同样的错误请求和合法请求复验。只重测合法请求不够，因为放宽之后还要确认越界请求仍能被纠正。

如果两次都判断正确，就没有观察到行为改善；如果 N1 才正确，也只能报告本次差异。手册在 N1 额外要求引用规则，提示文字也发生了变化，所以不能把改善全部归因于 `AGENTS.md`。需要进一步比较时，应另做双方请求完全一致的补充对照，并保留原始实验；本讲不要求用一次实验得出普遍结论。

## 5｜三件事要分开看

![规则读取、回答表现、程序检查需要分别核对](./图解/复验证据.png)

**图 2-3　规则读取、回答表现、程序检查需要分别核对**

*读图：分别核对规则读取、回答表现和程序检查。*

从左到右分别检查：规则有没有进入会话、回答是否遵守规则、程序检查结果如何。最后根据这些实际材料决定接受还是继续修改。

新会话说“我读到了”还不够，应核对可观察的指令上下文、文件读取记录或日志，并检查引用内容是否与当前规则一致。仅有回答中的自述不足以确认；无法确认时，就写“载入未验证”。

这里还要区分自动载入与按要求补读。Codex 会在开始工作时发现并组合适用的项目指令，工作目录及更具体的规则会影响实际使用的内容；因此不能要求每次都必须出现一条显式读文件命令，才承认有载入。反过来，追问之后成功读到文件，只证明这次补读成功。相关机制按 2026-09-26 的 [OpenAI 官方 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)核对；实际实验仍需记录自己入口中可观察到的证据。

比较 N0 和 N1，要引用回答中具体变化的句子；两次都正确，就写“没有观察到明显改善”。一次回答变好，也不能保证所有任务都有效。

最后按手册运行已有程序检查，保存命令、输出和退出码。检查通过能说明被检查的行为符合预期，但不能替代上面的规则实验。环境错误或运行了零个用例，都不能填写“通过”。

## 6｜从哪里开始，交什么

现在打开[实践操作手册](./实践操作手册.md)，从第 1 步确认自己的 L01 练习仓库开始，按七步完成。具体请求和命令都在手册里，不需要自己拼接。

个人材料放在该仓库的 `lesson-02-submission/`：规则修改前后副本、N0、N1 与正常维护对照，以及自己的 `记录.md`。在记录中说明条目的来源、取舍、实际结果和待复核问题；请同伴补查一项，再写下自己的结论。通过要求可对照[行动卡](./行动卡.md)。

完成后做一次迁移练习，换一个问题：“采购申请建好了，能不能先加库存、明天补审批？”说明申请与批准有什么区别、现在允许做什么、怎样检查库存没有被误改。这用于检验你能否把本讲的方法用到另一种情况。

两种情境使用的是同一种判断方法：记录齐全不能代替人工验收，申请建好也不能代替采购批准。先识别已经发生的事实，再指出还缺少的决定，最后提出当前允许的动作。采购情境下可以继续准备审批材料；入库要等待批准。本讲只评审计划，不运行入库操作。“检查库存未被误改”应写成未来可执行的核对方案，例如比较操作前后的库存与入库记录；没有执行，就不能写成已验证。

手册把这项方法扩展到库存、幂等、订单和采购，是为了检查迁移能力。当前练习仓库尚无 ERP 实现时，依据可以是明确的课程业务合同，但必须注明“后续开发约束，当前实现未验证”；没有实现或合同依据的判断，才记为待确认。约定成立与代码已经实现，是两件不同的事。

提交前，合上材料试着回答：为什么这条要求要长期保存？怎样写才不会误伤合法维护？若新会话判断错误，你先查什么？请同伴用一个新请求反驳你的规则，把反馈和修订写回 `记录.md`。能解释取舍并据此修订，才是本讲要保留的个人学习证据。


## 本讲留下什么，下一讲怎样接着用

本讲留下带代码依据的项目规则和前后对照记录。下一讲遇到新的库存导出需求时，规则仍继续有效；需要重新确认的是这次客户要什么、哪些不做、怎样验收。这正是长期规则与单次 Spec 的分工。
