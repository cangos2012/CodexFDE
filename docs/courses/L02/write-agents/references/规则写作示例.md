# 从项目事实写到可检查的规则

本文件用于卡在“知道原则，但不会落笔”时参考。以下是教学示例，不是可覆盖任意仓库的标准答案；示意方案均不是实际模型响应或执行结果。

## 例一：两个字段，怎样推导一条规则

场景：同事想把工作台查询结果改成中文，看见 `evidence_complete=true`，准备显示“人工验收通过”。先核对依据，再决定怎么写。

| 要查什么 | L02 参考仓库中的位置 | 可以支持的结论 |
|---|---|---|
| 完整性如何得出 | `workbench/bootstrap.py` 的 `_chain()`、`status()` | 核对导入的命令证据链及相关来源检查；不等于重新执行命令 |
| 人审状态从哪里来 | 同文件 `status()` 的 `acceptance` | 当前入口返回 `pending_human_review`，不能从完整性真值推出人工接受 |
| 项目要求怎样交付 | 已确认项目规则与任务范围 | 可以提出展示方案；不能用自动结果冒充人工决定 |

实现说明“当前返回什么”，负责人确认的要求说明“应保留什么”。目标项目字段、职责或要求不同就重新查证。

**产品决定：**“记录完整”和“人工接受”分别展示。当前入口不能证明完整的人审流转已经实现，方案不能把待开发能力写成已有功能。

| 候选规则 | 问题 | 取舍 |
|---|---|---|
| 必须确保状态正确 | 不知道“正确”指什么，无法检查 | 改写 |
| 禁止修改所有状态展示 | 连中文标签和布局调整都拒绝 | 舍弃 |
| 分别展示完整性与人审；允许调整措辞，但不能把完整性等同于验收通过 | 保护事实，同时允许合理维护 | 经项目要求确认后保留 |

可采用的**局部补丁示例**：

```markdown
## 查询展示约定

- 展示证据记录完整性与人工审核时，分别表达两项事实。
  不得仅因 evidence_complete 为 true 显示“人工验收通过”。
  acceptance 为 pending_human_review 时，应表达“等待人工审核”。
- 可以调整中文措辞和布局；提出展示方案时，说明如何检查
  “记录完整、人工尚未审核”这一组合，区分现有能力与建议新增能力。
```

不新增“所有修改必须重新批准”：本次问题在字段含义，正常授权内的分析和修改不应被无关确认阻塞。也不把该规则扩大成其他项目的固定审批制度。

**判读示例，不能填作实验结果：**

| 请求 | 符合规则的表现 | 不足以算符合 |
|---|---|---|
| 改进中文查询方案 | 引用真实入口，区分完整性与人审，提出检查情境 | 只复述“我会遵守规则” |
| 完整就显示人工通过 | 指出语义冲突，建议分开显示 | 先答应，再附风险提醒 |
| 保留事实，调整标签顺序 | 继续提出方案，说明影响范围 | 一律拒绝展示变化 |

## 例二：保留失败记录，仍可以整理展示

已确认边界是“原始失败证据需要可追溯”。它限制删改证据以掩盖失败；摘要折叠、筛选视图或排序可以允许，前提是原始记录仍可查。

```markdown
- 不得为呈现全成功而删除或改写原始失败记录。
  可以在摘要折叠详情，但应保留完整历史的查看路径。
  若该入口尚未实现，应在方案中标为待新增，不能宣称已可用。
```

“允许折叠”的理由是没有把失败改成成功，也没有破坏追溯；“拒绝删除”的理由是损坏原始证据。不能只看到“失败”两个字就拒绝。

## 例三：把命令的来源、范围、状态写清楚

课程参考仓库的 `eval/harness.py` 为 `--suite` 定义了 `blocking`，不是 `blockng`。目标仓库还要核对模块存在、项目虚拟环境与检查范围。

```markdown
## 验证与交付

- 在仓库根目录激活已核对的课程虚拟环境，确认解释器与源码路径。
  Windows PowerShell 与 macOS zsh 的通用阻断检查入口：
  `python -X utf8 -m eval.harness --suite blocking`。
  仓库自己有 `.venv` 时，也可直接调用解释器：
  Windows：`.\.venv\Scripts\python.exe -X utf8 -m eval.harness --suite blocking`；
  macOS：`./.venv/bin/python -X utf8 -m eval.harness --suite blocking`。
  沿用 L01 隔离区且本地没有 `.venv` 时，恢复原参考环境，不在隔离区重建。
- 实现变更运行相关测试和项目要求的阻断检查，报告实际退出码与失败项。
  仅提供方案时列建议检查，不把未运行的命令写成“通过”。
```

这是目标项目查证后可采用的写法，不是通用 Python 项目的要求。没有该模块就记录真实等价入口或检查缺口。

| 核验状态 | 交付中怎么写 |
|---|---|
| 读到配置，没有运行 | 已核对入口与参数；未执行 |
| 运行但环境缺依赖 | 执行受环境错误阻塞，附真实输出；功能未验证 |
| 有实际用例、退出码为零 | 本次对应检查通过，附覆盖范围与原始输出 |
| 自己拟了一份预期输出 | 教学示意或预期，不能作为执行结果 |

## 例四：已有 AGENTS 很长，怎样优化

不先按字数删减。对有问题的条目作出有依据的动作：

| 现有条目 | 决定 | 具体修改 |
|---|---|---|
| “保持专业，使用最佳实践” | 删除 | 没有增加可判断的项目约束 |
| “所有任务都运行完整业务演示” | 核对原要求后收窄 | 区分方案、文档和实现改动，保留真正适用的检查 |
| 旧模块路径已迁移 | 更新 | 查当前调用入口，替换路径并核对职责 |
| 根与局部文件重复且冲突 | 根据范围统一 | 公共边界保留一处，局部补特殊条件；验证实际发现 |
| 偶用的十几步部署流程 | 按需引用 | 注明何种任务读取哪份现有文档 |
| 负责人未决定采用哪个审批流程 | 暂不落入正式规则 | 保留冲突、候选和待决定事项，不自行选一个 |

修改后核对引用存在。将内容移到链接后面，不代表模型必然已经读到它。

## 迁移到文档协作项目

这个项目没有库存、采购或 Python。改查：正文与资料目录在哪里、引用需要什么依据、发布动作由谁决定、已有链接检查入口是什么。若项目明确要求“引用可追溯到原始来源”，就针对它写规则并设计检查；不要未经确认增加双人审批或课程工具。

复用的是查证、取舍、写动作、测边界的方法，不能携带 FlowERP 专有约定。
