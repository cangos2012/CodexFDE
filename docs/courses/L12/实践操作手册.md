# L12 实践操作手册

> 本资料由 AI 辅助整理，为课程赠送资料，用来辅助你实践练习，非必读资料。

本次交付两项相互验证的成果：FlowERP 经具名审批后入库；工作台显式表达开发、检查、返工、等待、审核和异常。把研发交付审核与采购审批分开，最终让状态记录与真实数据对上。

本讲有研发任务、采购审批、Graph 状态文件三类记录。`--state-file` 保存的是 Graph 的练习状态，不是采购审批单。首次运行用新文件，审核续做使用原文件；实际审核者、版本和理由来自本人流程，不能复制教学姓名。

开始操作前，遇到解释器、路径或输出问题，按[执行与排错说明](../../reference/实操手册执行与排错.md)核对。

### 本讲目录地图

```text
〈CodexFDE 控制仓库〉/                ← Graph 控制实验与任务提交的起点
├─ .venv/
├─ agent/graph.py
└─ .runtime/l12-…/                   ← Graph 状态文件与控制证据

〈独立 FlowERP 仓库〉/               ← 采购单与入库业务来源
〈工作台返回的隔离候选〉/            ← 实际建设与统一复验对象
├─ agent/、flowerp/
├─ eval/、tests/
└─ .course/experiment-source.json
```

`--state-file` 只保存 Graph 练习状态；采购审批仍在 FlowERP 业务数据中。两种状态不能放进同一文件，也不能用 Graph 的 `approved` 代替采购审批。

## 第 1 步：准备与独立预期

<!-- step-guide-1 -->
> **一句话说明：**先手写“批准”和“打回”两条路径中采购申请、库存和流程状态应该怎样变化。

开始本讲 FDE 实践时，先在[提交模板](SUBMISSION.md)的首次判断与需求记录回答：这次采购入库等待的是哪种批准，由谁负责，为什么等待或打回是当前合理结果？注明来源是实际观察、同伴试用还是教学设置，写下本次选择和暂缓范围，再请 Codex 协助调查。

在项目根目录使用项目 `.venv`。PowerShell 激活 `.\.venv\Scripts\Activate.ps1`；macOS/Linux 激活 `source .venv/bin/activate`。未安装项目时，激活后执行 `python -m pip install -e .`。以下相对路径均从项目根目录出发。

阅读[讲义](辅导资料.md)，在[提交模板](SUBMISSION.md)写下两套状态表：研发交付与采购单据分别处于哪些状态，谁根据什么批准。手算 A 从 10／2／8 到 17／2／15 的条件，写出未审批、重复请求及状态写入失败后的期望。

查看建设合同：

```bash
python -X utf8 -m workbench.cli course-contract --lesson 12
python -X utf8 -m workbench.cli course-spec --lesson 12
```

第一条显示课程合同；第二条生成文件并返回 `spec_path`，不会运行 Graph。返回后在编辑器打开该路径阅读，再继续第 2 节。它不是本人已确认的 Spec；默认输出会写到固定路径，已有个人修改时先保留版本，再用 `--output` 指定新路径生成。

采购服务属于独立 FlowERP，Graph 属于工作台。当前课程组合候选中的 `flowerp/` 来自客户项目，`agent/` 来自工作台，`eval/`、`tests/` 按来源记录区分；路径相对于返回的候选目录，不是 CodexFDE 根目录。本次 Spec 再收敛到实际文件。个人成果应在课程隔离候选中保留起点失败、范围内 Diff 和复验；终态仓库全绿不替代个人建设。

## 2 先观察 Graph 的真实控制范围

<!-- step-guide-2 -->
> **一句话说明：**用小实验观察 Graph 能控制流程顺序和恢复点，但不能替人作审批决定。

运行一个控制实验：

```bash
python -X utf8 docs/courses/L12/examples/graph_control_lab.py wait
```

依次将 wait 换为[入口表](README.md)中的十六种模式。每次先预测状态、检查次数、是否执行开发和是否保存结果，再比较输出。所有报告和审核人都明确是教学输入；包装程序退出 0 只表示观察符合当前程序行为。

优先完成四组比较：

1. demo 与 wait：自动演示完成和等待具名决定的区别。
2. resume、approve、reject：恢复等待、批准与打回是否重新检查。
3. blocking-failure、reject-at-limit：检查次数与 rounds 字段的区别。
4. eval-exception、malformed-state、save-error：异常在哪个阶段，能否留下结构化状态。

再观察 empty-report、stale-approval、unchecked-move，解释报告校验、审核对象绑定和允许边检查各自缺少了什么。approval-without-wait 和 terminal-rerun 用于比较未在等待时提交决定、已完成时再次运行的实际行为。

不要把临时标记文件的变化写成真实产品版本修复；也不要把教学 reviewer 字符串作为人的签字。实验不启动 Codex，参考 develop 节点没有真实开发动作。

## 3 检验审批与库存状态

<!-- step-guide-3 -->
> **一句话说明：**验证未经批准不能入库，具名批准后才能改变采购和库存状态。

**运行前确认：** `purchase_approval_lab.py` 自动使用独立 FlowERP 的解释器。先完成[客户环境检查](../../reference/实操手册执行与排错.md#product-environment)，再运行下面各模式。`status-write-failure`、`key-collision` 应退出 1 并留下业务报告，其余模式应退出 0；导入错误不属于预期业务失败。

每条使用新报告路径，再次实验换一个目录。实验创建临时数据库，不改个人产品候选。

```bash
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py approved --report-path .runtime/l12-business-01/approved.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py unapproved --report-path .runtime/l12-business-01/unapproved.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py blank-reviewer --report-path .runtime/l12-business-01/blank-reviewer.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py rejected --report-path .runtime/l12-business-01/rejected.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py replay --report-path .runtime/l12-business-01/replay.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py different-key --report-path .runtime/l12-business-01/different-key.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py status-write-failure --report-path .runtime/l12-business-01/status-write-failure.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py recovery-same-key --report-path .runtime/l12-business-01/recovery-same-key.json
python -X utf8 docs/courses/L12/examples/purchase_approval_lab.py key-collision --report-path .runtime/l12-business-01/key-collision.json
```

每次立即记录退出码：PowerShell 用 `$LASTEXITCODE`，macOS/Linux 用 `$?`。status-write-failure 与 key-collision 当前应退出 1，其余七项应退出 0。实验临时注册的 `l12_teaching_approval` 不是默认套件永久新增项。

每份 `name.json` 报告旁会生成 `name.states.json`，保存阶段名与五张表。即使断言失败，也保留 `final` 快照；读取 `before_receive` 和 `final` 判断拒绝是否留下修改。状态写入故障额外保存 `after_status_write_failure`，因此无需凭报错推测库存。

## 4 通过项目建设自己的 Graph

<!-- step-guide-4 -->
> **一句话说明：**在个人候选中实现可暂停、可恢复的审批 Graph，并保存每个节点的状态变化。

使用[设计提示词](prompts/01-区分状态与审核对象.md)，明确状态、允许边、守卫条件、动作副作用、保存时点和停止语义。每个会修改产品的节点应有真实执行入口，不能只修改标签。审核输入应绑定任务、候选、报告和实际决定者。

工作台组织本讲建设的入口：

```bash
python -X utf8 -m workbench.cli course-submit --lesson 12 --execute-code --actor "实际构建者姓名" --runtime-dir .runtime/l04-learning --execution-timeout 900
```

返回后按[提交结果与续做说明](../../reference/实操手册执行与排错.md#course-result)先保存退出码、任务编号和候选路径。退出 0 且状态为 `review` 才继续候选复验；非零先查原任务错误，不重复提交，不用控制仓库替代缺失候选。

这需要可用执行器与认证。核对实际任务、隔离候选与允许范围；该命令组织课程建设，不等于 Graph 的每条动作和人审已经验证。使用[实施提示词](prompts/02-实现转移与恢复.md)连接真实开发、统一 Eval、返工与审核。

把每次运行的报告、任务与状态材料保存在独立位置。参考 Graph 的修复草案写入固定 `.runtime/graph-repair-task.json`，默认 Harness 报告也可能被下一次覆盖；仅修改 `--state-file` 不能控制所有产物。自己的实现应让历史报告和审核依据能够恢复，不以最后一份摘要替代历史。

真实需求仍从工作台首页“事项与决策”进入，调研、执行、返工和验收在同一事项内组织。实验命令用于构建与核验，不另开独立日常研发页面。后端功能和首页尚未贯通的部分如实列出。

## 5 等待、恢复、批准和打回

<!-- step-guide-5 -->
> **一句话说明：**让具名审核者分别执行等待、恢复、批准和打回，证明决定来自人而不是自动化。

在自己的隔离候选中先运行正式默认入口，记录它属于演示策略还是已经改为自己的审核策略：

```bash
python -X utf8 -m agent.graph --max-rounds 3
```

再用全新状态路径进入明确等待模式。首次运行前在 PowerShell 检查 `Test-Path -LiteralPath .runtime/l12-review-01/state.json`；若已存在，先判断是续做原实验还是新建实验。新实验更换目录，并在下方等待和审核两条命令中使用同一路径；续做则保留原状态文件：

```bash
python -X utf8 -m agent.graph --max-rounds 3 --require-human-review --state-file .runtime/l12-review-01/state.json
```

当前参考行为：有效检查无阻断时为 awaiting_human_review，退出 3。存在阻断则可能停止，异常可能失败，不能预先填写预期状态作为实际结果。阅读报告和候选，保存等待时的状态副本及证据；副本使用新名称，保留前一版本。

再次运行同一等待命令，观察是否保持等待。由实际审核者检查对象仍有效后，使用其真实姓名提交决定：

```bash
python -X utf8 -m agent.graph --max-rounds 3 --require-human-review --state-file .runtime/l12-review-01/state.json --review-decision approve --reviewer "实际审核人姓名"
```

姓名占位必须替换；模型和教学脚本不能代替真实决定者签字。参考 CLI 只记录非空字符串，不提供身份认证；若通过正式界面交付，应验证实际身份、权限和报告对象绑定。

在另一独立运行目录建立等待状态，使用 reject 测试打回。保存打回前状态、意见、剩余轮数和新的检查结果。参考程序打回后会继续运行，可能立即再次进入等待；轨迹中的 develop 不证明已经改过代码。个人实现应保存真实修改和复验。

再验证审核期间候选发生变化、上限已耗尽、状态文件损坏和保存失败的行为。确认旧批准不能自动接受新候选，异常不被伪装成已保存或已完成，恢复不重复产生未授权副作用。

## 6 同一候选上的业务与流程复验

<!-- step-guide-6 -->
> **一句话说明：**在同一候选中同时复验 Graph 轨迹和 FlowERP 业务状态，确认两边一致。

使用[对账提示词](prompts/03-核对Graph与业务事实.md)，分别核对研发状态和采购状态。Graph completed 不应直接改变某笔采购的批准状态；采购 received 则必须对应合法审批与真实入库流水。

在整合候选运行：

```bash
python -X utf8 -m eval.harness --suite blocking --case purchase_requires_approval --case receiving_is_idempotent --report-path .runtime/l12-final-01/selected.json
python -X utf8 -m eval.harness --suite blocking --report-path .runtime/l12-final-01/blocking.json
```

同时运行个人新增的五表不变、部分提交、同键异对象、审核对象变化与恢复检查。默认两项只覆盖各自断言，不能替代本讲所有故障。记录命令、退出码、报告与最终候选。

请同伴从一条审核决定回查本次候选和报告，再从一条入库流水回查单据与业务审批人。重复请求与异常后的状态要能解释。真实执行、真实人审尚未完成的部分，保留为缺项，不用教学实验充当。

## 7 流程提炼与迁移

<!-- step-guide-7 -->
> **一句话说明：**总结哪些节点适合自动执行、哪些决定必须等待具名人员，并迁移到另一个审批场景。

使用 [state-handoff-review Skill](skills/state-handoff-review/SKILL.md)审查一次状态移交。保存反例输入、真实响应、漏判和修订。迁移到“测试通过后等待负责人选择发布时间”的发布需求，说明需要哪些状态、何时重验、哪些动作不能重复。

若进一步声称已经形成工作台闭环，须证明前一事项的经验在后一事项被召回并明确采用流程版本，执行仍经 Harness 与具名人审，复用失败推动修订或停用。当前闭环规格是建设要求，状态保存和流程资产登记不等于闭环完成。

## 排错

| 现象 | 先查什么 | 下一步 |
|---|---|---|
| 默认直接 completed | 是否启用人审或持久化 | 区分演示与真实审核策略 |
| 传批准却仍等待 | 提交决定前是否已处于等待 | 回查状态，不重复假定批准生效 |
| 打回后 rounds 超过上限 | 计数与实际动作是否不同 | 比较检查、开发次数及轨迹 |
| 状态文件不存在或损坏 | 错误发生在读取还是保存 | 保留原错误与最后可靠材料 |
| received 但数量不对 | 事务边界、事件键和目标流水 | 复现后修复并对账 |
| 重试后单据补齐 | 第一次是否曾部分提交 | 分别评价恢复能力与原子性 |

**交接时回到使用现场**：分别保存业务审批与研发审核的对象和理由；同伴检查未批准不能入库、打回后状态及恢复不重复，核对修订前后数量。迁移审批流程时重审审批权限、副作用和重试规则，记录所采用流程版本与新任务复验，不能只复制审核人字段。沿用本讲已有证据位置，不另交重复表格。
