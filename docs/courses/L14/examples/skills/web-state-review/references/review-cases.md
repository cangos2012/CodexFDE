# 审查练习

先预测，再实际使用 Skill，保留首次响应与漏判。以下仅为教学输入与预期识别点。

| 提交中的说法 | 应识别的缺口 |
|---|---|
| API 返回 200，所以采购页业务完成 | 200 只证明该请求成功，需核对返回状态与业务动作 |
| 列表查询失败但旧审批按钮仍可用，错误字样已出现所以通过 | 需检查旧数据新鲜度、按钮条件与后端实际拒绝 |
| 四列数值相等，数据都从同一个 JSON 复制 | 缺少 DOM、持久记录与独立业务预期的实际读取 |
| version 相同，所以事件肯定没变化 | 需核验版本更新语义，不能推断全部事件未变化 |
| 下载了最新补丁，因此这一任务可发布 | 缺少 Task、候选版本绑定及集成、发布证据 |
| 工作台离线隐藏了审核按钮，所以采购页离线也通过 | 两套读取逻辑与对象不同，需要采购列表的独立实测 |
| 客户库存 CSV 下载成功，说明 Task 已交付代码 | 业务数据导出不是研发候选包，缺本轮改动和文件关联 |
| 脚本用 maker 与 checker 完成审批，已有两人验收 | 两个账号只支持职责规则实验，不证明真人作出决定 |

沿[当前实践手册](../../../../实践操作手册.md#lesson-goals)，对照本人同一事项、同一候选对应的工作台任务证据与 ERP 业务证据，在本人隔离目录保存任务 ID、候选摘要、业务对象 ID，以及各自页面、接口和持久记录的读取结果。离线与恢复后分别回查原对象，比较任务详情与采购列表的实际行为。先给出自己的审查判断，再用记录核对；两套系统的对象 ID 分别绑定，不能混用，也不能把记录中的边界当成已经实际调用 Skill 的证明。

正常对照：同一 ID 的页面、接口和持久记录可核对；独立预期说明审批不增库存；查询失败保留身份并阻止过期审核；恢复后重新查询；下载文件与本轮候选匹配。审查仍应指出该证据实际覆盖的范围，不扩展为全部场景通过。
