# Web 状态与证据审查

适用于学员提交页面实现和操作证据后的复验。审查当前需求及允许范围，不因发现问题而自动改业务数据、重新执行任务或发布候选。

先列出事项 ID、Task ID、业务 ID、需求或候选版本、服务与运行目录。缺少这些关联时，将相应结论记为证据不足；不要按相似标题拼接不同对象。

依次核对：

1. 页面实际文案、状态与动作是否有同一对象的 API 和持久事实支持。请求成功、任务结束、业务完成分别判断。
2. 读取失败、写入结果未知、业务拒绝是否采用不同恢复方式；未知或陈旧信息是否仍可触发依赖最新状态的操作。
3. 乱序或切换对象时，旧响应是否能够覆盖新内容。区分浏览器读取序号与服务端对象版本，不从字段名称推断实现。
4. DOM、API、SQLite 与 ERP 规则是否真正分别检查；共享错误来源的相等数值不能替代独立业务预期。
5. 下载内容能否关联本轮 Task、候选和需求版本；区分预览、接受、集成、发布与实际效果。
6. 相关前端内容与构建产物是否含凭据；错误文本是否安全呈现；键盘与窄屏证据是否覆盖主要操作。

遇到跨页面或跨产物的结论，先拆开核对。任务详情失联后隐藏旧证据，不能证明采购列表也这样处理；verify 报告、研发候选补丁与客户库存 CSV 要分别识别来源和正常/失败路径。两个教学账号执行了职责分离规则，可以支持规则检查，不能写成两位真实业务人员已验收。

对失败截图先核对注入条件、原对象和恢复后状态，再判断是已证实缺口还是尚缺证据。保留失败画面与原始响应，不因参考实现存在缺口而降低本讲通过要求。提出最小修复范围与同条件复验步骤；是否实施修改由当前任务授权决定。

输出按“已证实问题、证据不足、已验证行为”组织。每项给出来源、用户影响、最小复现和接受条件。不要固定要求某种框架或轮询间隔，也不要把参考测试结果当成个人完成证明。

用 [review-cases.md](references/review-cases.md) 做初始判断练习；这些案例是教学输入，不代表 Skill 已通过真实调用验证。
