# 下载补丁后怎样确认它属于刚才的任务

一个下载按钮可能返回库存CSV、检查报告或代码补丁。先确认产物类别，才能判断后续要核对什么。本例复核已有库存筛选任务 `TASK-402AD958DB` 的实际补丁，解释代码下载的正向路径，与本讲采购库存CSV形成对照。

## 从任务记录到实际文件

本次使用原任务数据库的只读快照，通过项目现有HTTP下载处理器读取原补丁。没有启动新的Codex开发，没有修改原任务状态，也没有经过原工作台页面点击。完整开发背景见[库存筛选真实案例](../../cases/L16-库存余额筛选真实执行案例.md)。

核对顺序是：找到任务的“日常研发交付包已保存”事件，读取事件中的补丁路径与SHA-256摘要，再请求该任务的补丁地址，最后比较下载字节的摘要与改动文件。

| 核对对象 | 本次实际结果 | 支持的判断 |
|---|---|---|
| 请求的Task | TASK-402AD958DB | 下载有明确任务归属 |
| HTTP响应 | 200 | 这次请求确实返回文件 |
| 附件名称 | TASK-402AD958DB.patch | 文件类型是代码补丁，不是项目压缩包 |
| 文件长度 | 18,992字节 | 文件非空；长度本身不能证明内容正确 |
| 事件摘要与下载摘要 | 完全一致 | 下载字节与事件登记的产物一致 |
| 修改范围 | 两个页面文件、两个测试文件 | 与该任务批准的四文件写集一致 |
| 任务状态与审核人 | review，审核人为空 | 下载成功后仍待审核 |

四个修改文件为 `web/index.html`、`web/app.js`、`tests/test_http_api.py` 和 `tests/flowerp_inventory_filter.test.cjs`。完整摘要及响应保留在讲师本机历史记录 `patch-download-observation.json` 中，不随 Git 发布。原补丁下载前后摘要未变。学生沿[当前实践手册](../实践操作手册.md#lesson-goals)在本人隔离目录生成下载记录，核对自己的任务与候选。

## 为什么摘要相同仍不能宣布交付完成

摘要相同证明取到的是登记的字节，不判断代码是否满足业务要求。还要结合原需求、候选版本、检查范围和实际操作结果决定是否接受。该任务目前仍为待审核；本次没有代签、集成或发布，也没有把补丁应用到其他项目。

把补丁改名为“最终版”不会改变任务状态。补丁只记录相对于特定起点的改动，接手者仍需正确的基线与应用方法，不能把它当成可直接启动的完整项目。

## 用于本讲实践

完成自己的采购页修复后，在原事项找到对应Task与补丁入口，实际下载，再核对原需求、修改范围及文件摘要。保留没有补丁、文件失效和内容变化时的失败记录，不用另一任务的“最新文件”代替。

本例补齐了历史真实代码产物的HTTP下载观察，不替代L14本人修复、原页面下载操作或独立人审。库存CSV与代码补丁分属业务结果和研发结果，应分别核对对象，不能相互顶替。
