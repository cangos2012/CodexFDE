# 实操手册执行与排错

先确认正在操作哪个仓库。CodexFDE 保存工作台与课程；FlowERP 保存客户业务，两者各用自己的虚拟环境和运行目录。下面的命令从 CodexFDE 根目录运行。

## 沿用前一讲时，先核对代码和解释器

L01 的隔离区默认借用参考仓库的 `.venv`，隔离区内没有 `.venv` 不一定是准备失败。L02、L03 沿用该成果时，先按 [L01 手册的“故障定位与中断恢复”](../courses/L01/实践操作手册.md)激活原参考环境、回到原隔离区；不要重新创建 L01 起点覆盖进度。已有独立环境则激活自己的环境。每个新终端都需重新选择解释器。

在实际练习目录运行以下只读检查：

```text
python -X utf8 -c "import sys,workbench; from pathlib import Path; print('当前目录:', Path.cwd()); print('Python:', sys.executable); print('虚拟环境:', sys.prefix != sys.base_prefix); print('源码:', workbench.__file__)"
```

`虚拟环境` 应为 `True`，`源码` 必须位于本次练习目录。解释器来自参考仓库可以成立，源码误指向参考仓库则不能继续验收个人实现。激活失败时先解决环境，不继续使用终端中残留的系统 Python。

## 先确认每条路径属于哪个项目

| 对象 | 源码归属与路径基准 |
|---|---|
| 控制工作台 | CodexFDE 的 `workbench/`、`agent/`、工作台 Eval 与测试；根目录没有客户业务包和客户页面 |
| 客户产品 | 独立 FlowERP 仓库的 `flowerp/`、`web/`、业务 Eval 与测试；使用客户自己的虚拟环境 |
| 当前课程教学候选 | L04+ 部分实验仍将两仓库源码组合到临时目录，路径相对于命令返回的候选根目录；这不是新的客户源码仓库 |

课程的 `write_scope` 是候选中的路径上限，不能据此在 CodexFDE 根目录新建 `flowerp/` 或 `web/`，也不能直接修改已登记的客户源仓库。先保存任务编号、候选绝对路径及来源记录，再确认具体允许文件。候选中的 `eval/`、`tests/` 可能包含不同项目的检查，不能只凭同名目录判断归属。

来源记录由实际准备方式决定：源码快照使用 `.course/product-source.json`，实验副本使用 `.course/experiment-source.json`，旧标签候选使用工作台返回的基线与隔离记录。来源不足时先补查；不得拿当前客户仓库的绿灯代替候选验收。候选修改不会自动写回任一源仓库。

当前组合候选机制仍待迁移为两个独立项目候选；本文说明现状，不表示该迁移已经完成。已有候选按原任务续做，不用它作为新的控制仓库源码快照。

## 先检查环境和课程入口

```powershell
.\.venv\Scripts\python.exe -X utf8 -m workbench.cli environment-check
.\.venv\Scripts\python.exe -X utf8 -m workbench.cli course-status
.\.venv\Scripts\python.exe -X utf8 -m eval.harness --suite blocking
```

没有 `.venv` 时，Windows 先运行 `py -3.11 -m venv .venv`，再运行 `.\.venv\Scripts\python.exe -m pip install -e .`。macOS / Linux 使用 `python3.11 -m venv .venv`，将后续解释器路径换为 `.venv/bin/python`。`course-status` 需要匹配的课程合同及 Git 标签；缺标签时先核对仓库来源，再执行 `git fetch origin --tags`。不要强制覆盖本地已有标签。

工作台安装自检不要求客户项目。需要检查客户环境时运行 `python -X utf8 -m workbench.cli environment-check --product`，或用 `--product-root` 指定独立仓库路径。它在客户解释器中检查包来源，失败返回非零退出码；不启动服务或初始化业务数据。

默认 Eval 只验证工作台。客户业务检查在独立 FlowERP 仓库执行；本讲的显式业务用例由工作台通过独立进程委托，不要向工作台环境安装或复制 `flowerp/` 来绕过缺失项目。

<a id="product-environment"></a>

### 已登记 FlowERP，命令仍提示找不到项目

当前命令的客户项目解析读取默认工作台运行目录的登记；在 `.runtime/l04-learning` 等自定义目录的页面登记，不一定会被另一个终端自动发现。先在该操作终端显式指定客户仓库，输入实际绝对路径：

```powershell
$env:FLOWERP_PROJECT_ROOT = (Read-Host '独立 FlowERP 仓库绝对路径').Trim().Trim('"')
python -X utf8 -m workbench.cli environment-check --product
```

macOS / Linux：

```bash
printf '独立 FlowERP 仓库绝对路径（不加引号）：\n'
read -r FLOWERP_PROJECT_ROOT
export FLOWERP_PROJECT_ROOT
python -X utf8 -m workbench.cli environment-check --product
```

退出 0 且 `ok: true` 后才继续需要客户项目的步骤。非零时查看 `checks` 中失败项：仓库路径错误就纠正路径，客户 `.venv` 缺失则回到该仓库完成安装。新终端需重新设置；服务进程使用它启动时的环境。

**实验源码来源：** 业务观察脚本会自动转到独立客户解释器；需要修改代码的实验在新目录组合两个仓库的源码，并写入 `.course/experiment-source.json`，记录原文件路径和哈希。候选 Eval 使用该副本的业务检查。检查环境通过后即可按手册继续；已有记录按原会话续做，重跑故障实验使用新输出目录。修复前后证据见[本轮检查记录](操作手册检查-2026-09-15.md)。

<a id="course-result"></a>

## course-submit 返回以后怎么做

适用于 L04 起的课程提交。带 `--execute-code` 的命令会实际执行，可能需要数分钟；尚未返回时保留终端，不重复提交。结束后立即保存退出码（PowerShell：`$LASTEXITCODE`；macOS/Linux：`echo $?`）和完整输出，再按下表处理：

| 看到什么 | 下一步 |
|---|---|
| 退出 0，`task.status` 为 `review` | 保存 `task.id`、`isolation.path` 和报告；在该候选上按本讲步骤独立复验，再交人审核。待审核不等于已接受 |
| 退出非零，但返回了 `task.id` | 先按原编号查 `task.error` 与事件中的失败原因，保留原候选；不要马上重新创建任务 |
| `rework` | 核对执行失败、Eval 或红绿差分的具体原因，按本讲返工步骤处理 |
| `failed` / `dead_letter` | 保留终态记录，修复前置问题后再按本讲规则创建新任务，并关联原编号 |
| 参数错误、缺标签或尚无任务编号 | 本次尚未取得业务失败证据；核对参数、课程版本、标签及客户环境后重试 |
| `isolation` 为空或没有候选路径 | 先查准备与执行事件；不要猜目录，也不要把控制仓库当候选继续检查 |

在同一控制目录查询原任务，两类终端均可用，输入运行目录的绝对路径和真实编号：

```text
python -X utf8 -c "import subprocess,sys; r=input('原工作台运行目录绝对路径：').strip(); t=input('真实 Task ID：').strip(); (r and t) or sys.exit('路径和编号不能为空'); sys.exit(subprocess.run([sys.executable,'-X','utf8','-m','workbench.cli','task-show',t,'--runtime-dir',r]).returncode)"
```

页面没有任务时先核对网页与 CLI 的运行目录。`review`、`completed` 不能直接重复 `task-run`；重开终端也不需要重新初始化。课程候选未必自带 `.venv`，可在候选目录调用已确认的控制解释器，先核对 `workbench.__file__`、`eval.__file__` 及候选中的 `flowerp.__file__` 均指向该候选，再运行检查。

`unittest discover -s tests -v` 还包含读取客户源码的课程集成测试，运行前须准备并指定独立 FlowERP。全量 CI 在 `.runtime/flowerp-project` 检出固定客户提交并创建独立虚拟环境；版本固定在 `.github/workflows/eval.yml`，升级该版本时需要重新验证课程缺陷夹具。日常工作台 Eval 与安装自检不需要客户仓库。

## 按失败位置处理

| 现象 | 核查与下一步 |
|---|---|
| 找不到 `gateway`、`agent.ops` 或旧 Hook | 这是旧版本入口；使用当前讲义及 `python -m workbench.cli --help`，不要恢复旧模块 |
| 找不到 `flowerp` 或独立仓库 | 在首页登记 FlowERP，或设置 `FLOWERP_PROJECT_ROOT`；核对该仓库自己的 `.venv` |
| 不认识 `--report` | `eval.harness` 使用 `--report-path`；`workbench.ci_evidence` 使用 `--report`，两者参数不同 |
| PPT 链接不存在 | `slides/` 与 `.pptx` 不随 Git 发布，见[课件获取说明](../courses/课件获取与本地检查.md) |
| 用例不存在、报告为空 | 停止执行，核对候选、检查名称和环境；不能把环境错误当作产品起始红灯 |
| 检查通过但任务仍待审核 | 先独立复验，再由具名审核者决定；绿色检查不自动完成产品验收 |
| 网页行为与代码不同 | 核对端口、运行目录与服务版本；按[启动说明](../../README.md)重启对应服务，保留原数据目录 |

## 保存能复现的证据

记录仓库路径、提交或候选身份、完整命令、退出码、报告与首次错误。修复后在同一候选、同一检查口径下复验，另存修复后的结果，不覆盖首次失败。课程实验中的模拟身份和示意输出不能用作学生本人证据。

工作台默认报告在 `.runtime/reports/`。需要另存时指定一个新路径，例如 `python -X utf8 -m eval.harness --suite blocking --report-path .runtime/reports/manual-recheck.json`。这条命令验证当前工作台，不替代客户业务用例或课堂迁移任务。


## 开课前批量验证实验

先完成上面的双仓库安装与客户环境检查。在 CodexFDE 根目录、已激活的虚拟环境运行：

```text
python -B -X utf8 scripts/audit_course_experiments.py --output-dir .runtime/course-labs-check-01
python -B -X utf8 -m unittest tests.test_course_experiments -v
```

第一次命令逐项运行本地实验模式，核对预期退出码、报告存在性和导入错误；末尾 `failed` 应为空，命令退出 0。每项完整命令与输出保存在指定目录，汇总为 `summary.json`。再次检查改用 `course-labs-check-02` 等新目录；只复查一讲可追加 `--lesson 9`。故障模式的预期退出 1 或 2 会记录为检查通过，因为此时验证的是系统确实拦截了错误。

第二条命令验证来源边界、文件交付、L05/L06 实验衔接、失败报告映射、事项重启后持久化和摘要导出；维护夹具不充当学生作品。任一命令非零时，根据首个失败项修复后复查，保留旧日志。

这两项用于开课前工具检查。学员仍须完成自己的实现、实际 Hook 接入、远程 CI 和具名复验；本地参考实验不会代替这些学习证据。
