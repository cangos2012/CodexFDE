# 本机个人研发平台：运行、操作与验收边界

本页说明本仓库的工作台入口与受控操作。日常使用从根路径 `/` 的“事项与决策”开始：选择项目，澄清需求，确认范围，交付候选，核对证据，具名验收，再决定是否集成、发布和复用经验。代码检查通过、生成了草稿或保存了记录，都不能代替真实业务验收。

## 1. 运行一个明确的工作台

在本仓库根目录使用独立 Python 虚拟环境。已有环境时直接使用，不要新建或替换已有运行数据。

```powershell
.venv\Scripts\python.exe -m pip install -e .
.venv\Scripts\python.exe -B -X utf8 -m workbench.cli environment-check
.venv\Scripts\python.exe -B -X utf8 -m workbench.cli serve-workbench --runtime-dir D:\workbench-data\personal --enable-code-execution --enable-advanced-runtime
```

打开 `http://127.0.0.1:8001/`。`--enable-code-execution` 开启经首页确认方案的隔离代码执行；`--enable-advanced-runtime` 开启同一事项内的 Session、工具授权和受管多 AI 分工。当前实现通过本机 Codex CLI 执行，需已安装并登录；这不表示已接入官方 app-server。

`--runtime-dir` 是你选定的工作台数据目录，数据库为其中的 `workbench.db`。省略时由 `workbench/runtime_paths.py` 读取本仓库 `.runtime/services.json`，保留已有安装路径；配置损坏时会报错，不能把新建空库当成旧数据恢复。FlowERP 的源码、虚拟环境和数据库独立准备，不能与工作台数据目录混用。

`/api/health/live` 表示进程可响应，`/api/health/ready` 表示当前数据库、数据实例、恢复状态及空间满足就绪检查。`/api/health` 也会在数据不完整时返回 503，不能把进程活着当成可交付。高级提交超时或刷新后，首页保留原提交键的待核对提示；只读核对回执和当前事项，再决定结束提示，不自动重发。稳定性机制和商用剩余条件见[可靠性记录](workbench-reliability.md)。

端口已占用时先核对实际服务，不要仅凭端口号认定它是本仓库工作台。可使用 `--port 8002`，入口仍为 `http://127.0.0.1:8002/`。8010 保留历史、Profile 和 Session 的只读兼容界面，页面提供当前上游工作台链接；日常交付与运行控制在首页同一事项内完成。

工作台使用自定义端口（例如 8101）时，可选 8010 兼容入口也须明确指向同一根地址：`.venv\Scripts\python.exe -B -X utf8 -m workbench.cli harness-serve --port 8010 --workbench-url http://127.0.0.1:8101`。这不会自动迁移旧数据或重放旧任务。

## 2. 登记项目并完成一条交付

1. 在“管理项目”登记独立 Git 工作区，填写该项目的检查命令。命令是 JSON 参数数组，首项为本机可执行文件的绝对路径。例如 `["D:/product/.venv/Scripts/python.exe","-B","check.py","{report_path}"]`。检查程序需输出符合项目 Eval 合同的逐项报告；单纯退出码 0 不足以证明交付通过。
2. 在“项目目标与里程碑”填写目标、验收条件和关联事项。架构依据填写项目内已有文件的相对路径，保存其哈希。里程碑依赖不得循环；前置未完成时关联事项会被阻断。架构文件变化后重新核对计划，不能继续使用旧依据。
3. 从“事项与决策”新建真实需求，指定操作人和验收人，澄清目标、非目标、验收条件与允许修改的文件。先查看冻结方案，再授权执行。
4. 工作台从当前源码（包括已纳入来源清单的未提交修改）建立隔离候选。执行前检查、Codex 过程、实际 Diff、执行后项目 Eval 和失败记录留在事项中。候选通过检查后仍待验收人核对；实际失败保留为失败，返工产生新一轮证据。
5. 验收人根据真实 Diff、当前报告与业务行为接受或打回。接受后再核对集成方案；候选或来源源码变化时重新准备、复验。验收与集成是两个动作。

里程碑完成必须有关联事项和具名验收依据；关联事项重新打开后会显示需要复验。文本中的“完成”不自动变成真实接受记录。

旧 `/api/v1/execution/daily-plans` 仅适配已确认事项，需要 `initiative_id` 与当前 `expected_revision`，返回原事项方案的授权别名。授权仍由该事项的共享 `DeliveryRuntime` 执行；自由填写另一份需求或范围不能另建执行队列。历史未绑定事项的日常方案只供读取，需要回到首页重新核对。课程隔离执行入口保持课程合同。

## 3. 在同一事项内控制运行与分工

“运行与分工”显示本事项的 Task、Session、执行 Profile、候选哈希、预算和运行事件。Profile 的选择须重新核对；更换或停用插件后，旧方案不能继续凭旧配置授权。

暂停会请求停止受管进程并保留候选，等待终态后再恢复。恢复须核对候选哈希，重新冻结并授权新一轮；不会重放旧写任务。取消同样保留已有执行证据。重启后被中断的运行需要明确处理，不能将中断当成完成。

受管分工支持 2～4 个子任务。先填写目标、角色、允许修改范围及交接依据，核对没有重叠写入后再启动。子任务在各自隔离副本执行，最终串行整合并对父候选复验；子任务检查绿不等于父事项验收通过。时间预算和可取得的 token 用量属于整个事项，恢复和子任务不能重置为无限预算；缺失可靠用量时保留“不可用”边界。

工具调用需要的授权在本事项内显示。核对具体工具、参数、候选版本与权限后作出决定；原始调用、决定和执行结果保留为事件。具名操作不是多人账号认证，首版面向本机个人使用。

## 4. 预览、发布和回退

在管理项目时可登记预览命令、健康检查与本机发布配置；保存配置不会启动进程。预览从已经核验的候选启动，命令占位符限 `{workspace}`、`{runtime_dir}`、`{port}`。任务与事项面板均先读取预览说明并明确确认；已登记配置的通用预览展示具体命令、候选哈希、独立目录和目标地址。当前预览由工作台服务持有，关闭预览网页不会结束进程；关闭工作台服务统一请求资源收尾，失败时记录异常并保留待清理资源，不能保证一次关闭全部成功。单项预览的显式停止界面仍待补齐，存在未收尾预览时不能发布备份包。

登记配置的通用项目预览保存并消费绑定候选哈希与配置版本的具体计划。旧 FlowERP 兼容预览保留现有启动入口，在启动时检查当前证据与配置；它尚不保存并消费浏览器展示的冻结预览计划。

首版受控发布支持本机 HTTP 目标。流程是：源码集成完成 → 选择已登记环境 → 查看本次冻结制品及具体命令 → 明确授权发布 → 保存进程回执与健康检查 → 指定验收人记录真实业务验证。健康检查通过只进入待业务审核；没有业务证据和人审时保留待审状态。

需要回退时先核对该发布对应的已登记回退命令，再授权执行。回退是人工决定的真实动作；流程失败不会自动改写客户源码或自动重试发布。回退失败也保留真实状态与回执。未配置命令的项目不能声称已经具备自动发布能力。

## 5. 从事项 A 提炼，在独立事项 B 复用

在 A 的“从真实轨迹生成草稿”中选择已验收任务，或已具名接受的实际失败反馈。生成器冻结任务、反馈与证据文件哈希，使用只读 Codex CLI 生成记忆或流程草稿，并要求结论引用存在的证据编号。生成有独立的 `generation_id`、输入/输出哈希、状态与过程文件；取消或失败不会修改 A 的交付任务。

人先核对生成内容、适用范围、排除条件和引用，再填入候选表单保存。生成结束不自动审核、试用或发布。保存时会重查来源、生成状态和引用；证据变化时不能继续采用旧草稿。

流程 v2 固定为四阶段，不允许任意 DAG 或流程内任意 shell 命令：

| 阶段 | 负责人 | 必须保留的依据与停止边界 |
|---|---|---|
| `precheck` | Harness | 已确认方案、可执行前置检查及阶段检查；文件缺失或内容不符即停止。 |
| `implement` | Codex | 实际修改与 Diff；核对该阶段必需文件和内容，违反约束即保留候选并停止。 |
| `eval` | Harness | 已登记项目阻断 Eval、阶段检查及必需文件；报告缺失、失败或被替换不能进入接受。 |
| `review` | 人 | 当前候选、Diff、Eval 与具名人审；人未判断时保持待审。 |

参数须明确定义并全部填写；替换后的文件路径仍只能位于候选项目内。`file_exists` / `file_contains` 提供结构化前置和阶段检查，`required_files` 指定实现或 Eval 后必需文件。四类必需证据固定为 `precheck`、`implementation_diff`、`project_eval`、`human_review`。`stop`、`outputs` 和 `rollback` 说明供人核对，结构化阶段检查执行实际阻断；`recovery` 固定为保留候选并重新确认新方案。v1 旧快照和哈希保持兼容，不能把旧说明文字追称为 v2 的可执行阶段约束。

流程候选经独立具名审核可供 B 试用；B 必须是不同事项，明确选择资产版本、填写参数并冻结采用快照。B 执行和人审通过后，再由真实具名人决定发布流程版本。记忆可经非提炼者具名审核后激活，但仍需 B 的明确采用与结果才能证明跨事项闭环。复用失败会记录失败并触发停用或修订；修订创建新版本，不改历史采用快照。

查看因果链时应能追溯“来源 A → 草稿与人审 → B 明确采用 → B 执行和验收 → 发布或失败修订”。只有单项测试、一次交付或反馈登记时，仍不能称为跨事项闭环。统计只使用真实留存记录；缺少样本的提效和重复失败减少指标显示待测。

## 6. 迁移到另一个目录或另一台机器

首页“跨机器迁移”先读取真实项目、源码清单、解释器和外部依赖；核对后准备迁移包并下载。准备计划先经过写入门闩，打包时经过排他维护门闩；运行、排队、生成草稿、预览或部署未结束时不能发布备份包。

包内包括工作台数据库和纳入备份范围的原始文件证据。项目源码、Python 虚拟环境、Node 环境、客户数据、密钥和 Git worktree 外部登记不由此包完整携带，须在新机器单独准备。备份验证通过表示包内完整性通过；不表示外部项目能运行。

在新机器先停服，准备一个新的空运行目录和对应的外部项目环境。把旧绝对路径到新绝对路径的 JSON 对象保存为 `mapping.json`，不填写占位路径，也不改历史数据库中的路径字符串。例如：

```json
{
  "D:\\work\\product": "E:\\projects\\product",
  "D:\\work\\product\\.venv\\Scripts\\python.exe": "E:\\projects\\product\\.venv\\Scripts\\python.exe"
}
```

使用新机器本仓库的虚拟环境执行：

```powershell
.venv\Scripts\python.exe -B -X utf8 -m workbench.cli verify-workbench-backup E:\transfer\workbench.zip
.venv\Scripts\python.exe -B -X utf8 -m workbench.cli restore-workbench-migration E:\transfer\workbench.zip --runtime-dir E:\workbench-data\personal --mapping-file E:\transfer\mapping.json
.venv\Scripts\python.exe -B -X utf8 -m workbench.cli verify-workbench-migration --runtime-dir E:\workbench-data\personal
```

运行目录本身的旧→新映射由恢复器生成。映射只用于读取历史引用；恢复的数据库和原始证据 payload 字节及原有哈希不重写。再次迁移会携带并展开上一轮映射，保留上一轮映射文件原文。

初次环境核验比较迁移包中的项目源码清单，检查真实 Git 根登记和登记可执行程序。Python 须为 Python 3.10+ 独立虚拟环境；Node 等非 Python 程序须实际 `--version` 成功。环境缺失时证据可已恢复，但执行环境仍未就绪，旧任务不会重放。解决真实缺失后重新运行核验；不要伪造源码一致性结果。

首次源码证明成功后，新事项的 preflight 检查当前登记、Git 与执行环境，并冻结当前源码；后续正常源码修改不会永远受旧迁移清单锁住。显式 `verify-workbench-migration` 仍用于复核包的初始来源，源码已开展新开发时不应把它当成每天的源码冻结操作。

复制、包校验或引用核对失败时，目标保留 `workbench-restore-failed.json`，清理已安装文件并阻止将该目录当作完整恢复启动。保留失败目录作为证据，查明原因后换一个新的空目录重试；已有目录不会被覆盖。原路径恢复使用 `restore-workbench-backup`，迁移使用上述专用命令。

## 7. 最终完成判断

在一个真实受控需求上核对以下结果：冻结 Spec 与范围一致；执行前后检查、Diff 和过程可追溯；具名验收人作出真实判断；集成和发布有明确目标与授权；真实业务验证留有证据；A 的经验被独立 B 明确采用并保留结果；失败可修订或停用；迁移包在空目录恢复并核验后可以重新准备新事项。

自动化测试只验证这些机制的受控路径和拒绝路径。真实 Codex 运行、具名独立人审、发布后的业务效果，以及另一台机器的环境确认，需要实际执行和判断后分别记录；缺少其中任一项，应保留为待执行或待审。

实现入口：`workbench/workbench_server.py`（工作台服务）、`workbench/delivery_runtime.py`（事项运行）、`workbench/project_plan.py`（项目计划）、`workbench/deployment.py`（本机发布）、`workbench/learning.py` / `workbench/learning_generation.py`（经验复用与辅助蒸馏）、`workbench/migration.py` / `workbench/reference_paths.py`（迁移核验与只读引用映射）。
